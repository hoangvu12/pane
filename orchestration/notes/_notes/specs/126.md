#126 Instant file search: Pane indexes the home folder and keeps the index current on Windows, macOS and Linux
## Problem Statement

Pane's file search finds only the files of one folder the user grants the Files default extension. It lists that folder again on every visit of root search, stops at 8 folders deep, 5,000 files and 20,000 entries, keeps no index and watches nothing ([files](https://github.com/hoangvu12/pane/blob/main/docs/files.md), [ADR 0017](https://github.com/hoangvu12/pane/blob/main/docs/adr/0017-host-lists-a-granted-folder-for-an-extension.md)). A user who wants a document from their Downloads, a project from another folder, or a file they saved a minute ago either cannot find it from Pane or has to choose a folder first and hope it is small enough. Files beyond the limits are silently out of reach, a large folder costs a full walk each time root search is opened, and nothing tells the user which files a search could never see.

Raycast indexes the whole home folder once, keeps it current from the file system's own change records, and answers a file query as fast as it answers a command query: on the machine where Pane's research ran it indexed 450,097 entries (405,792 files and 44,305 folders) in 12.9 seconds into a 61.8 MB index, and re-indexed a changed file in 4 to 10 ms, without administrator rights ([research](https://github.com/hoangvu12/pane/blob/main/docs/research/raycast-deep-dive.md#windows-integration)). Pane, which positions itself as small and fast, is currently far behind on the feature users reach for most after applications.

## Solution

Pane's host keeps a name index of the user's home folder, and of any other folder the user adds, on every system. The index is built once in the background, stored in Pane's cache folder, caught up at start from what the file system recorded while Pane was not running, and kept current while Pane runs by watching the folders. A query is answered from the index in milliseconds, so files appear in root search as the user types, and a Search Files command searches the whole index with filters, recent files and file actions.

The index honours `.gitignore` and similar ignore files, skips hidden entries, caches, temporary folders and system folders by default, and lets the user add folders, exclude folders or patterns and change those defaults in Settings. It needs no administrator rights on any system. It aims to be faster than Raycast: on the same machine and the same home folder, a first index in less than 12.9 seconds and smaller than 61.8 MB.

The Files default extension stays a disableable default extension ([ADR 0001](https://github.com/hoangvu12/pane/blob/main/docs/adr/0001-small-core.md)): it supplies file rows to root search and the Search Files command from the host's index, and while it (or another package that uses the index) is disabled, Pane neither indexes nor watches anything. The single granted folder and its scan policy stop being file search's limits: [ADR 0034](https://github.com/hoangvu12/pane/blob/main/docs/adr/0034-file-search-indexes-the-users-home-folder.md) records the user's decision and supersedes those parts of ADR 0017 for file search. What ADR 0017 decided and ADR 0034 keeps still holds: the host, not the extension, reads the file system; files are named by the ids the host gives them; and the host checks a file again before opening it. ADR 0017's refusal to open programs and scripts, which ADR 0034 left for this specification, is replaced by the user's decision recorded in [ADR 0037](https://github.com/hoangvu12/pane/blob/main/docs/adr/0037-a-command-declares-its-mode-and-host-functions-decide-what-happens-after-it-runs.md): file search may open anything Raycast's would, but its own Enter never runs a program by accident. A program found by file search is shown as a file and runs only through an explicit Run action.

What each system gets differs only in how Pane learns what changed:

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| Catch-up at start | The NTFS change journal, read without administrator rights from where Pane left off, per volume | FSEvents' history, replayed from the last event Pane saw, per volume | A reconciling walk that re-reads only folders whose modified time changed |
| Live changes | Directory change notifications (`ReadDirectoryChangesW`) | FSEvents | inotify, with a reconciling fallback where the watch limit is reached |
| Background priority | Background thread mode (low I/O priority) and EcoQoS | The background quality-of-service class (throttled I/O) | Idle I/O priority and the lowest CPU priority |
| Home folder | `%USERPROFILE%`, without `AppData` | `$HOME`, without `~/Library`; macOS asks the user once per protected folder (Desktop, Documents, Downloads) | `$HOME` |

## User Stories

### Finding files from root search

1. As a launcher user, I want files from my whole home folder to appear in root search as I type their names, so that I can open any of my files without choosing a folder first.
2. As a launcher user, I want file rows to appear as quickly as command rows, so that searching for a file never feels slower than searching for an application.
3. As a launcher user, I want file rows listed after commands, applications and quicklinks that match, so that file names do not push the things I launch every day down the list.
4. As a launcher user, I want only the best few files in root search with a row that searches all files for my query, so that root search stays short and the rest is one Enter away.
5. As a launcher user, I want a file whose name is exactly what I typed to rank above one that merely contains it, so that precise queries find precise files.
6. As a launcher user, I want a file whose name starts with my query, or whose words start with my query's words, to rank above a match in the middle of a word, so that partial names behave as I expect.
7. As a launcher user, I want the folders a file is in to count when my query names them ("invoices 2026"), so that I can narrow a common file name by where it lives.
8. As a launcher user, I want recently modified files to rank a little higher than old ones of the same match, so that the version I am working on comes first.
9. As a launcher user, I want folders found as well as files, so that I can jump to a project folder by name.
10. As a launcher user, I want letter case and accents ignored ("resume" finds "Résumé"), so that I do not have to type names exactly.
11. As a launcher user, I want each file row to show the file's name, the folder it is in and the system's icon for its type, so that I can tell same-named files apart at a glance.
12. As a launcher user, I want Enter on a file row to open the file with the system's handler for its type, so that it opens where it normally would.
13. As a launcher user, I want Enter on a folder row to open the folder in the system's file manager, so that I can continue browsing there.
14. As a launcher user, I want Enter on a program, script or shortcut to a program that file search found never to run it, so that a mistyped query or a file a browser dropped into my Downloads cannot run code by accident.
15. As a launcher user, I want such a program shown as a file, with Enter showing it in the file manager and a Run action that runs it when I choose that action, so that I can still run my own tools from file search on purpose.
16. As a launcher user, I want Open With, Copy Path and the other file actions on a program too, so that a program is as manageable as any other file.
17. As a launcher user, I want a file that was deleted or moved since it was indexed to be explained rather than opened, so that a stale row never opens the wrong thing.
18. As a launcher user, I want file results to keep arriving while the rest of root search is already shown, so that a busy disk never delays my other results.

### The Search Files command

19. As a launcher user, I want a Search Files command whose own search field searches every indexed file, so that I can look for a file without root search's other results.
20. As a launcher user, I want Search Files to show my most recently modified files before I type, so that the file I just saved is right there.
21. As a launcher user, I want to filter Search Files to files only, folders only, or kinds such as documents, images, audio, video and archives, so that I can find a picture without wading through same-named text files.
22. As a launcher user, I want to sort results by relevance or by when they were modified, so that I can find the newest of many matches.
23. As a launcher user, I want more results to load as I scroll, so that a broad query is not cut off at a fixed number.
24. As a launcher user, I want to see a file's full path, size, kind and modified date for the selected row, so that I can choose the right copy before opening it.
25. As a launcher user, I want actions on the selected file — open, open with another application, reveal in the file manager, copy its path, copy its name, copy the file itself and move it to the Recycle Bin or Trash — so that common file chores need no file manager.
26. As a launcher user, I want moving a file to the Recycle Bin or Trash to ask first and to be undoable from the system's bin, so that a slip never destroys a file.
27. As a launcher user, I want to reach Search Files from root search with my query already typed, so that I can widen a root search into a full file search.
28. As a launcher user, I want Search Files to say that indexing is still running and how many entries it has found, so that I understand why a file is not there yet on a first run.

### Building and keeping the index

29. As a new user, I want Pane to index my home folder by itself the first time file search is on, so that file search works without setup.
30. As a new user, I want the first index to start only once I have used Pane, or after a short delay, so that indexing does not compete with my login.
31. As a user, I want indexing to run at background priority, so that my editor, build or game never stutters because Pane is indexing.
32. As a user, I want results from what is already indexed while the first index runs, so that file search is useful from the first minute.
33. As a user, I want a file I create, rename, move or delete to be reflected in file search within about a second, so that results match what is on disk.
34. As a user, I want Pane to catch up with what changed while it was not running without walking my whole home folder again, so that starting Pane stays cheap.
35. As a Windows user, I want Pane to catch up from the NTFS change journal without administrator rights, so that I need no elevated service for file search.
36. As a macOS user, I want Pane to catch up from FSEvents' history, so that changes made while Pane was closed are found at once.
37. As a Linux user, I want Pane to catch up by re-reading only folders that changed, so that a restart costs far less than a first index.
38. As a user, I want Pane to fall back to a reconciling walk when the system's change records are gone (the journal was recreated, FSEvents' history was purged, too much changed), so that the index is never silently wrong.
39. As a Linux user, I want Pane to keep working when the system's limit on watched folders is reached, by re-checking the unwatched folders instead and telling me so, so that a big home folder does not break file search.
40. As a user, I want the index kept on this computer only, readable only by me, and never sent anywhere, so that a list of my files does not leak.
41. As a user, I want Pane to stop indexing when free disk space runs low and to say so, so that the index never fills my disk.
42. As a user, I want a folder that changes constantly (a build output, a log folder) to be taken out of the index with an explanation and a way to put it back, so that churn does not keep my disk and CPU busy.
43. As a user, I want indexing to pause while the computer sleeps and resume after it wakes, so that a sleep never leaves the index half-updated.
44. As a laptop user, I want watching to cost nothing while nothing changes, so that file search does not drain my battery.

### What is indexed

45. As a developer, I want files my `.gitignore` files ignore (build outputs, dependencies) left out of the index by default, so that my results are my files, not generated ones.
46. As a developer, I want to turn the `.gitignore` rule off, so that I can find an ignored file such as a local configuration when I need it.
47. As a user, I want hidden files and folders left out by default and a switch to include them, so that dotfiles and system clutter appear only when I want them.
48. As a user, I want caches, temporary folders, `node_modules`, `AppData` on Windows and `~/Library` on macOS left out by default, so that the index stays small and fast.
49. As a user, I want to add folders outside my home folder, such as a second drive's projects folder, so that file search covers where I actually keep files.
50. As a user, I want to exclude folders or name patterns of my own, so that private or noisy places stay out of my results.
51. As a user, I want network shares and removable drives left out unless I add them, so that an unplugged or slow drive never stalls indexing.
52. As a user, I want files of a removable drive I added to be hidden while it is unplugged and back when I plug it in, so that its files are not lost from the index between uses.
53. As a OneDrive, iCloud Drive or Dropbox user, I want online-only files listed by name without Pane downloading them, so that indexing never fills my disk or uses my network.
54. As a user whose home folder holds folders I cannot read, I want them skipped and counted, so that one locked folder does not stop indexing.
55. As a macOS user, I want Pane to explain before macOS asks whether Pane may read my Desktop, Documents and Downloads folders, and to tell me which ones I refused and how to allow them, so that the system's prompts are not a surprise.

### Controls and status

56. As a user, I want a File search page in Settings showing whether the index is building, current or stopped, how many entries it holds and when it was last caught up, so that I can trust what file search finds.
57. As a user, I want to rebuild the index from Settings, so that I can recover from anything that went wrong.
58. As a user, I want disabling the Files extension to stop indexing and watching at once, so that turning the feature off really turns it off.
59. As a user, I want uninstalling the Files extension to delete its index, so that no list of my files is left behind.
60. As a user who had granted Files a folder, I want that folder kept in what is indexed when file search changes to the index, so that I lose nothing I could find before.
61. As a user running two Pane copies on one data folder, I want the second to say that file search is in use by the other, so that two indexers never corrupt one index.

### Extension authors and contributors

62. As an extension author, I want to search Pane's file index from my own command, in Rust, JavaScript or TypeScript, so that my extension can offer files without walking the disk itself.
63. As an extension author, I want each result to carry the id Pane gave it together with its path, name, kind, size and modified time, so that I can present and copy file details freely while Pane opens files it checked.
64. As an extension author, I want to declare in `pane.json` that my package uses the file index, so that Pane keeps it current exactly while a package that needs it is enabled.
65. As an extension author, I want to read whether the index is building and how far it has got, so that my command can say why results are incomplete.
66. As a contributor, I want the index, the walker and each system's change source behind seams the tests can drive, so that catch-up, live changes and fallbacks are tested deterministically on every system.
67. As a contributor, I want a reproducible benchmark that builds a home-sized tree and measures indexing time, index size, memory and query latency, so that "faster than Raycast" is a measured claim, not a hope.
68. As an assistive-technology user, I want file rows to carry their name, folder and kind as accessible text, so that a screen reader can tell same-named files apart.

## Implementation Decisions

### Scope and decision provenance

- **Decided by the user (2026-10-06, decision 8), recorded in [ADR 0034](https://github.com/hoangvu12/pane/blob/main/docs/adr/0034-file-search-indexes-the-users-home-folder.md):** index the user's home folder like Raycast, with a minidex-like name index, NTFS change-journal catch-up, directory watching, `.gitignore` honoured, exclusions the user can change, network and removable drives left out by default, and no administrator rights or system service; be faster than Raycast, whose measured index was 450,097 entries in 12.9 s and 61.8 MB on disk, on the same machine and folder. ADR 0034 supersedes ADR 0017's single granted folder, its refusal to grant the home folder, its scan policy and its exclusion of an index and watching, for file search. Also decided: extensions are trusted ([ADR 0002](https://github.com/hoangvu12/pane/blob/main/docs/adr/0002-trusted-extensions-and-open-distribution.md)) and may run system programs (decision 6), and the user's direction is "as flexible as possible" for extension authors.
- **Kept from ADR 0017, as ADR 0034 says:** the host reads the file system; files are named by host ids; the host checks a file again before opening it.
- **Decided by the user (2026-10-06), recorded in [ADR 0037](https://github.com/hoangvu12/pane/blob/main/docs/adr/0037-a-command-declares-its-mode-and-host-functions-decide-what-happens-after-it-runs.md)'s "Open things":** file search may open anything Raycast's would, but its own Enter never runs a program by accident. A program (an executable, a script, a shortcut to a program) is shown as a file and runs only through an explicit action ("Run"), with Show in File Explorer, Open With, Copy Path and the others as further actions. This replaces ADR 0017's refusal, which ADR 0034 left for this specification to revisit.
- **Decided by this specification, as ADR 0034 asks it to:** the folder grant stays for packages other than file search (below).
- **Proposed defaults the user delegated ("like Raycast, as flexible as possible"):** Ctrl+Enter on a program is Open With, and Run is an explicit action; root search shows at most 5 file rows plus a "Search Files" row; file rows appear from 1 character of query, with no longer minimum; iCloud Drive is not a default root on macOS.
- **Proposed defaults in this specification (not separately confirmed):** the per-system catch-up and watching mechanisms beyond NTFS, the default exclusions beyond those ADR 0034 names, the targets' numbers below the Raycast baseline, the action set, the thresholds of the safety valves, the settings page's contents, and the new manifest declaration and host interface. Each is stated so a ticket can implement it and a reviewer can change it.
- The cross-platform rule (Q8) holds: one behaviour on every system, with only the change source, background priority and permission prompts differing, each explained where it shows.

### Where the index lives

- The index is the host's, in `pane-core`, as the folder listing was ([ADR 0017](https://github.com/hoangvu12/pane/blob/main/docs/adr/0017-host-lists-a-granted-folder-for-an-extension.md)) and the applications list is ([ADR 0015](https://github.com/hoangvu12/pane/blob/main/docs/adr/0015-host-finds-and-opens-applications-for-an-extension.md)): a WASI guest has no folders to read, the walk and watching must never run on the extension runtime's shared thread, and one index serves every package that uses it. The core owns matching and ranking ([ADR 0006](https://github.com/hoangvu12/pane/blob/main/docs/adr/0006-raycast-style-search-with-extension-providers.md)); for files, the index's own scoring orders files among themselves.
- **Modules:** a file index module (the store, its scoring and its query); a walker (the parallel first walk and reconciling walks, applying the scope and ignore rules); one change source per system (catch-up at start and live events, behind one trait so tests can drive it); an indexer coordinator (scheduling, priorities, safety valves, status); the launcher's integration (root search rows, the Search Files command's search, opening, the File search settings page's operations); a host interface for guests.
- **Activation:** a package declares in `pane.json` that it uses the file index (proposed name `"fileIndex": true`). The index is opened, caught up and watched only while at least one such package is enabled and not paused; when the last one is disabled, paused or uninstalled, watching stops at once and the index stays on disk; uninstalling the last one deletes it. This keeps lazy activation ([ADR 0005](https://github.com/hoangvu12/pane/blob/main/docs/adr/0005-lazy-activation-and-managed-dependencies.md)) without running guest code to learn it.
- **Start:** catch-up runs when Pane starts (it is cheap); a first full walk, or a reconciling walk the catch-up asks for, waits until the launcher is first shown or 60 seconds after start, whichever comes first (Raycast defers its full index until its window is first focused).
- **Storage:** in Pane's cache folder (`%LOCALAPPDATA%\Pane\cache` on Windows, `~/Library/Caches/Pane` on macOS, `$XDG_CACHE_HOME/pane` on Linux), since it can always be rebuilt; readable by the user only (mode 0700 on macOS and Linux, a protected DACL for the user and SYSTEM on Windows, as `credentials.json` is written). It carries a format version; an index of another version is rebuilt, never read. The index folder is locked; a second Pane on the same cache folder does not index and says that another Pane is using file search.
- **The engine:** a name index in the shape of minidex (an FST-based segmented index with a memtable, a write-ahead log, background compaction and tombstones for deletions). Whether Pane depends on the MIT-licensed `minidex` crate (0.38 at the time of writing, pre-1.0 and changing quickly) or writes its own index of that shape is decided by the first slice's measurements; either way Pane's index format is Pane's, versioned as above.

### Scope and rules

- **Roots:** the home folder (`%USERPROFILE%` on Windows, `$HOME` on macOS and Linux) plus folders the user adds. A folder granted to Files under #29 that lies outside the home folder, or inside a default exclusion, is added as a root once when the index replaces the listing, and the grant is then forgotten.
- **Always excluded:** Pane's own data, cache and log folders and the index itself; the system's recycle and system folders (`$RECYCLE.BIN`, `System Volume Information` and the other Windows setup folders Raycast skips); folders marked as caches with a `CACHEDIR.TAG` file.
- **Excluded by default, each a user setting:** hidden entries (a name starting with `.` on every system; the hidden and system attributes on Windows); files and folders ignored by `.gitignore`, `.ignore` and the user's global Git ignore file, read as Git reads them without running `git`; `node_modules`, `*.tmp`, `*.temp`, folders named `tmp`, `temp`, `cache` or `caches` in any letter case; `AppData` on Windows and `Library` on macOS directly in the home folder; network and removable volumes.
- **User rules:** extra roots, excluded folders and excluded patterns (in `.gitignore` syntax), the hidden and ignore-file switches and the volumes switch, kept in Pane's own record beside its settings (not extension data). Changing any rule reindexes only what the change affects where it can, and walks the affected roots otherwise.
- **Entries:** files and folders, named as the system names them; a name that is not valid Unicode is indexed and shown with replacement characters while its exact name is kept for opening. Links and junctions are indexed as entries but never followed, so no cycle or second copy of a tree can occur. Each entry keeps its kind, size, modified time and volume.
- **Bundles:** on macOS an application or other package bundle (`.app`, `.photoslibrary` and the like) is one entry; its contents are not indexed.
- **Online-only files** (OneDrive Files On-Demand and other cloud-file placeholders on Windows, dataless iCloud Drive and File Provider files on macOS) are indexed from their directory listing alone; Pane never reads their contents, so nothing is downloaded.
- **macOS privacy prompts:** macOS asks the user before an application reads Desktop, Documents and Downloads (and removable and network volumes). Before the first walk, Pane's File search status says that macOS will ask; a folder the user refuses is skipped and listed on the File search page with how to allow it under System Settings › Privacy & Security › Files and Folders. Full Disk Access is never required. Because Pane is not signed yet, macOS may ask again after an application update replaces the program; this is recorded as a limit until signing exists.

### Catching up and watching, per system

- **Windows:** per NTFS volume holding a root, Pane keeps the change journal's id and the next update sequence number it has read. At start it reads the journal from there through the unprivileged journal read, which needs no administrator rights, and applies the changes under its roots. The first walk reads folders with file ids, so journal records (which name files by id and parent id) resolve to index entries without extra calls. It walks instead when the journal's id changed (it was recreated), when the records Pane needs were already discarded, when a root's volume has no journal (FAT, exFAT, a network share) or when the catch-up would be larger than a walk. Pane never creates or resizes a journal, which would need administrator rights. Live changes come from directory change notifications on each root (the `notify` watcher development mode already uses); a notification buffer that overflows makes Pane reconcile the affected root. The first slice confirms the unprivileged read's behaviour on the supported Windows versions; where it is refused, catch-up is a reconciling walk as on Linux.
- **macOS:** Pane keeps the last FSEvents event id it applied and the volume's FSEvents UUID. At start it opens a stream from that id, so FSEvents replays what changed while Pane was not running, then keeps the same stream for live changes. It walks instead when the volume's UUID changed, the event ids wrapped, or FSEvents says a folder must be rescanned (its history was purged or coalesced), reconciling only that folder where FSEvents names one.
- **Linux:** the system keeps no change history Pane can read without privileges (fanotify needs them), so catch-up is a reconciling walk that compares each folder's modified time with the index's and reads only folders whose time changed (a folder's time changes when an entry is added, removed or renamed in it); a changed file's size and time are refreshed when it is shown. Live changes come from inotify, one watch per folder. When the per-user watch limit is reached, Pane keeps the watches it has (shallowest folders first), reconciles the unwatched folders with the same walk every few minutes, and says on the File search page how many folders are not watched and which system setting raises the limit.
- **Every system:** changes are batched (about 100 ms) before they are applied; a live change is visible to queries within one second of the file system reporting it. Reconciling walks use the same rules as the first walk. Indexing work pauses when the system goes to sleep and resumes no sooner than a few seconds after it wakes, and its time limits count awake time only.

### Priority and safety valves

- The walker and indexer run on threads of their own, never the window's or the extension runtime's, at background priority: background thread mode (low I/O and memory priority) and EcoQoS on Windows, the background quality-of-service class on macOS, idle I/O priority and the lowest CPU priority on Linux. A query is never run at background priority.
- **Churn quarantine:** a folder producing more than about 1,000 changes a minute for 3 minutes in a row is taken out of the index and listed on the File search page with the reason and an action to include it again (proposed thresholds).
- **Ceilings:** a walk stops at 5 million entries and says so; indexing stops writing when the volume holding the cache has less than 1 GiB free, and resumes when there is space again (proposed values).
- **Hung folders:** a folder that does not answer within a bounded time is skipped for this walk and listed, so a stalled network mount or dying disk holds up only itself.

### Targets

The user decided that Pane should be faster than Raycast. The comparison is made on the machine where Raycast was measured, with the same home folder, and is recorded with the conditions (cold and warm file system cache, the scope and rules used):

| Measure | Raycast (measured) | Pane target |
| --- | --- | --- |
| First index of the home folder (≈450,000 entries) | 12.9 s | below 12.9 s; aim for half (proposed) |
| Index on disk | 61.8 MB (≈137 bytes per entry) | below 61.8 MB (proposed) |
| A changed file re-indexed | 4–10 ms | under 10 ms, visible to queries within 1 s (proposed) |
| Query over the full index | not measured | 95th percentile under 10 ms in the host (proposed) |
| Start-up catch-up after 10,000 changes | not measured | under 1 s on Windows and macOS (proposed) |
| Idle cost | not measured | no periodic work while nothing changes, except Linux's fallback reconciliation and added network volumes (proposed) |

The private memory the index adds while idle is measured and recorded with [#4](https://github.com/hoangvu12/pane/issues/4)'s workload; its ceiling is proposed after the first measurement, not before.

### Matching and ranking

- Names and paths are tokenized on word boundaries and separators, then case-folded and accent-folded for matching ("resume" finds "Résumé"), consistent with root search's transliteration (the "Root search like Raycast" specification (#122)).
- Scoring follows the shape Raycast's index uses: an exact name above an exact stem, above a name prefix, above a word start, above a match inside the name, above a match only in the folders; a match inside a word and a match only in the extension score lower; recently modified entries are boosted a little, decaying with age; a folder ranks slightly above a file of the same score; query words in order and close together rank higher; a deep path loses a little. The weights are tuned against fixtures, not copied.
- A query containing `/` or `\` matches path segments in order. There is no query language (no `kind:` or `ext:` operators); filters are structured options, as in Raycast.

### In root search

- The Files default extension keeps answering root search through `root-results`, now from the index: its call returns at once from the host and never waits for a walk. Root search lists at most 5 file rows (proposed default, delegated), after commands, applications and quicklinks that match (as since #29), and a "Search Files for “<query>”" row that opens the Search Files command with the query. File rows appear from 1 character of query; there is no longer minimum (proposed default, delegated). The blank query shows no file rows.
- File rows are listed within root search's per-provider time budget and late answers are merged when they arrive (the "Root search like Raycast" specification (#122)); until then the #29 rule holds that a slow file answer never holds up other providers.
- A file row's title and subtitle are the host's: the entry's name and its folder (relative to the home folder as `~`). Its result kind reads File, or Folder for a folder (a new result kind, added to the glossary). Its icon is the system's icon for the path (the icon model of the "Extension commands like Raycast" specification (#120)).
- No use of a file row is recorded for learning: ADR 0030 records uses only for results with a lasting identity, and a file is not one (the "Root search like Raycast" specification (#122)). This specification adds no learning of its own.

### The Search Files command

- Files gains a Search Files command that owns its search field (the command search of #30, extended by the "Extension commands like Raycast" and "Extension UI you can design" specifications): a blank query lists the most recently modified entries; a query lists matches by score, or by modified time when the user sorts that way; more results load as the list scrolls (pagination); a dropdown filters by kind — all, files, folders, documents, images, audio, video, archives, applications — classified from the name's extension, the same table on every system.
- The selected entry shows a detail with its full path, kind, size and modified time (the "Extension UI you can design" specification (#121)'s Detail with metadata). Thumbnails and previews are out of scope.
- Actions (the "Extension commands like Raycast" specification (#120)'s action panel and host functions): Open (primary), Show in File Explorer / Finder / the file manager (Ctrl+Enter, the secondary action, as the "Extension commands like Raycast" specification (#120)'s Files rework has it), Open with… (the system's list of applications for the type), Copy path, Copy name, Copy file (the file itself, as the system's clipboard format for files), Move to Recycle Bin / Trash (destructive style, confirmed, using the system's undoable bin). A program's row orders them differently, as under Opening: Show in the file manager (Enter), Open with… (Ctrl+Enter), then Run. On Linux, Reveal asks the desktop's file manager to show the item through the freedesktop file manager interface, and opens the containing folder where none answers; Move to Trash follows the freedesktop trash layout.
- While the index is building, the command shows the loading state and "Indexing … (N found so far)"; a stopped index says why and offers the File search page.

### Opening

- Opening names the entry by the id the host gave it ([ADR 0034](https://github.com/hoangvu12/pane/blob/main/docs/adr/0034-file-search-indexes-the-users-home-folder.md)) and goes through the host, which checks again that the path exists, is the kind indexed and is not a link, then hands it to the system's handler, as #29 does today (the `open` crate's handler per system, without a shell). A missing or changed file is explained ("it no longer exists", "it is now a folder") and nothing opens.
- **Programs run only through an explicit action (the user's decision, ADR 0037).** A program is any entry of the types #29 refused, the same on every system: Windows executables, scripts and installers (`exe bat cmd com js jse vbs vbe wsf wsh hta msi msp scr pif ps1 cpl reg`); `.lnk` shortcuts and `.url` files, whose target the user cannot see from the row; macOS applications and command files (`app command tool terminal workflow`) and anything inside an application bundle; `.desktop` files; and any file with an executable bit on macOS and Linux. Such an entry is found and listed like any file, with the system's icon and kind ("Program", "Script", "Shortcut").
- **Its Enter is safe.** The primary action of a program's row, in root search and in Search Files, is Show in File Explorer (Finder on macOS, the file manager on Linux). Enter never runs it. The row's footer names that action, so the user sees what Enter will do.
- **Run is explicit.** Ctrl+Enter, the secondary action, is Open With… for a program (proposed default, delegated), and "Run <name>" is the first action after it in the actions panel (the "Extension commands like Raycast" specification (#120)), listed before Copy Path, Copy Name, Copy File and Move to Recycle Bin/Trash. Run has no default chord, so no Enter variant runs code. Choosing Run hands the checked path to the system's handler, as opening any file does. A shortcut runs its target, a script its interpreter, and an installer starts. No further confirmation is asked, because choosing Run is the confirmation.
- **Until the actions panel exists.** If this specification's root search rows land before the "Extension commands like Raycast" specification (#120)'s actions panel, a program's row offers only its safe Enter, and Run arrives with the panel. Nothing runs a program in between.
- Folders always open in the file manager. An application bundle on macOS is a program and follows the rule above.
- The granted-folder capability keeps ADR 0017's refusal for its own `open-file` results, since its packages never offered a Run action.

### For extensions

- A new host interface (proposed `pane:extension/file-index`), imported by any package declaring `"fileIndex": true`: a search taking the query and options (kind filter, kind category, sort, limit, offset) and answering entries with the id the host gave them, the absolute path, name, kind, size, modified time and volume; a status answering whether the index is building, current, stopped or off, how many entries it holds and why it stopped. The search never waits for a walk: it answers from what is indexed. The extension never reads the file system for the index. A root result names an entry by its id (the `open-file` root action), and the host checks it again and applies the program rule above: Enter on a program's row shows it, never runs it. The path is carried as text because extensions are trusted and authors want to show, copy and act on it. A command that chooses to open or run an entry explicitly uses the host's open functions of ADR 0037, which open what the command names, programs included. That is the command's explicit action, as Run is file search's own.
- Rust through `pane-guest`, JavaScript and TypeScript through a module of the same name, with types, as every host interface. Samples in the three languages replace the granted-folder samples as file search's examples.
- **The folder grant stays for other packages (decided here, as ADR 0034 asks).** The capability (`"folderAccess": true`, Pane's "Choose folder…" row, `list-folder`, `open-file` with its ids and checks) remains as ADR 0017 describes, for a package that wants an exhaustive listing of one folder the user chooses, including a folder the index excludes; its scan policy stays its own. Files stops using it, and a test fixture keeps it covered once the samples move to the index.

### The File search settings page

A page in Settings (Pane's own controls, kept in Pane's own record): the index's state and counts, when it was last caught up and how; the roots (the home folder and added folders) with Add folder and Remove; excluded folders and patterns with Add and Remove; switches for hidden entries, ignore files and network and removable volumes; folders that could not be read, that macOS refused, that are not watched (Linux) or that churned, each with its reason and remedy; Rebuild index. Settings search finds it. While no enabled package uses the index, the page says file search is off and why.

### Glossary and records

- New glossary terms: **File index** (the host's index of names under the index scope, kept in Pane's cache, current while a package that uses it is enabled) and **Index scope** (the roots and the rules deciding what is indexed). **Granted folder** and **Scan policy** stay, no longer naming file search; their entries change to say so. The Pinned home's "Pane shows no recent use" note is unaffected: Search Files' blank-query list shows recently modified files, not recent use.
- The scope rules and per-root catch-up cursors are Pane's own records; the index itself is cache.
- Documents to update with the implementation: files.md (rewritten for the index), root-search.md, current-decisions.md item 10's file-search part, ADR 0017's status (superseded for file search by ADR 0034).

### Delivery order

1. A measured first slice (prototype, platform-independent where possible): the walker and the index engine on Windows, macOS and Linux, measured with the benchmark below against the targets, deciding between the `minidex` crate and Pane's own index, and confirming the unprivileged journal read.
2. The index, its scope and rules, root search's file rows and the host interface, with catch-up and watching on all three systems.
3. The File search settings page and the safety valves.
4. The Search Files command with filters, detail and actions, after the "Extension commands like Raycast" and "Extension UI you can design" specifications provide the action panel, host functions, list dropdown, pagination and detail.

## Testing Decisions

- A good test drives Pane as a user or an extension would and checks what is found, opened or said; it never asserts the index's internal layout, file names inside the cache folder or which thread did the work.
- **Primary seam: the `Launcher` public interface** with the real Files guest (Rust) and the new JavaScript and TypeScript samples, over a fixture folder that stands for the home folder (the test names it, as tests already replace the home folder), with the real index and the real watcher, waiting deterministically for the index to settle (a `wait_for_file_index` alongside `wait_for_updates`, `wait_for_schedules` and `wait_for_services`). Prior art: `crates/pane-core/tests/files.rs` (fixture folders with Unicode names, a recording opener, a lister the test holds up), `applications.rs` (a host capability under root search) and `update.rs` (a background thread waited on deterministically).
- What those tests cover: found by exact name, stem, prefix, word start and folder words, with case and accents ignored; folders found and opened through the recording opener; hidden, ignored, `node_modules`, cache-tagged and excluded entries absent, and present once their switch is turned off; a created, renamed, moved and deleted file reflected after the index settles; a restart over the same cache folder after changes made while stopped, found without a full walk where the system keeps history (the index reports how it caught up — journal, event history or walk — for tests to assert); a journal or history that is gone leading to a walk with the same result; a format version change rebuilding; an added root and a removed root; a removable root absent and present; rows placed after title matches, capped, with the Search Files row; a slow index holding up no other provider; a stale row explained at Enter; a program, a script and a shortcut found and listed, Enter on each revealing it (the recording opener sees a reveal, never an open), and the Run action handing the checked path to the opener; an entry replaced by a link after it was indexed refused at Enter; an id from an older index or another package's search not opened; disabling Files stopping watching (a change made then is not found until it is enabled again, then caught up); uninstalling deleting the index; a granted folder from #29 migrated into the roots; a second launcher on the same cache folder refusing to index; the host interface from each language.
- **Window tests** (`crates/pane/tests`, real key events): root search's file rows and their accessible names; the Search Files command's blank-query list, filter dropdown, sorting, pagination, detail and actions once the "Extension commands like Raycast" and "Extension UI you can design" specifications land; the File search settings page's controls, status and Rebuild, through Settings search too. Prior art: `settings.rs`, `launcher_settings.rs`, `command_search.rs`.
- **Platform tests**, opt-in where they need the real system, run by CI's legs: Windows — the unprivileged journal catch-up on the runner's NTFS volume with Pane stopped between changes, and a journal whose cursor is too old leading to a walk; macOS — FSEvents replay from a saved event id, and a changed volume UUID leading to a walk; Linux — inotify live changes, and the watch-limit fallback driven through the change source's seam (the limit cannot be lowered without root). Prior art: `hotkey_adapters.rs` and the clipboard adapter tests.
- **Benchmark:** a reproducible task that generates a home-shaped tree (by default 450,000 entries, about 9 files per folder, with ignore files, hidden folders and deep paths) and measures the first index (cold and warm), the index's size, idle private memory, query latency percentiles over a fixed query set, and catch-up after a batch of changes. It runs on demand, not per push; a reduced tree runs in CI's Linux leg with a generous ceiling as a regression guard. The comparison with Raycast runs once on the user's machine against the real home folder and is recorded in the research folder with its conditions.
- **Native smokes,** one phase per system: index a fixture home, find and open a file by name, create a file and find it, restart Pane after a change and find it, and (macOS) record the privacy prompt's handling.
- Screen readers, macOS's privacy prompts on a signed build and behaviour on real network shares are release-validation items, not claimed by these tests.

## Out of Scope

- Searching file contents, OCR, semantic or embedding search, and using the system's content indexes (Windows Search, Spotlight, Tracker or Baloo); a later specification may add them.
- Reading the NTFS master file table, an elevated service or helper of any kind, or any feature that needs administrator rights.
- Thumbnails, Quick Look and other previews beyond the metadata detail.
- The system's own recent-files lists (Windows Recent and jump lists, macOS recents) and recent use of files opened through Pane beyond what the "Root search like Raycast" specification (#122) records.
- File operations beyond the listed actions (rename, move, compress, share), and a query language.
- Indexing other users' folders, the whole system disk by default, or anything outside the roots.
- Live watching of network shares (they are reconciled by walks when added).
- Retiring the granted-folder capability, which stays for other packages.
- A confirmation before Run, and a default chord that runs a program.
- Script commands (decision 7) and importers from other launchers (decision 10).

## Further Notes

- Depends on the "Extension commands like Raycast" specification (#120) (action panel, host functions for open, open with, reveal and move to bin, confirm dialog, the icon model and the rework of default extensions in which Files owns a search field), the "Extension UI you can design" specification (#121) (List with dropdown, pagination, loading state, Detail with metadata) and the "Root search like Raycast" specification (#122) (root search's time budget, late results, transliteration and learned ranking). The index, its root search rows and the host interface do not wait for them; the Search Files command's screen does.
- Raycast's index is the MIT-licensed `minidex` crate in a worker, scoped to the home folder with `.gitignore` honoured, caches and `AppData` excluded, at background priority, with churn quarantine and a low-disk floor, caught up from the NTFS change journal at start and watched with `ReadDirectoryChangesW`, without admin rights; its NTFS master-file-table scanner exists but is switched off in 2.6.1. Pane takes the ideas; it does not copy Raycast's code ([research](https://github.com/hoangvu12/pane/blob/main/docs/research/raycast-deep-dive.md)).
- [ADR 0034](https://github.com/hoangvu12/pane/blob/main/docs/adr/0034-file-search-indexes-the-users-home-folder.md) records decision 8 and what it supersedes in ADR 0017; this specification settles the two things it left open. Programs run only through an explicit Run action, as the user decided (ADR 0037), and the folder grant stays for other packages.
- Settled since the first draft (proposed defaults the user delegated): Ctrl+Enter on a program is Open With and Run is an explicit action; root search shows at most 5 file rows plus "Search Files"; file rows need no more than 1 character of query; iCloud Drive (inside `~/Library`) is not a default root on macOS, and a user can add it as a root.
- Root search's typed-folder listing (Tab to browse a typed path, the "Root search like Raycast" specification (#122)) is covered by ADR 0034's file access and needs no ADR of its own; it lists only the folder the user typed and does not use the index.

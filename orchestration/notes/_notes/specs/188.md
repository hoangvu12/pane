#188 Idle cost: nothing runs while Pane is hidden and quiet, and nothing is redone that did not change
## Problem Statement

Pane is meant to cost nothing while the user is not using it (Q3, low resource use, in the [decision index](https://github.com/hoangvu12/pane/blob/main/docs/current-decisions.md)). File search already holds to this: "While nothing changes, nothing runs" ([files](https://github.com/hoangvu12/pane/blob/main/docs/files.md)). The rest of the app does not. A code read on 104a5dac found work that runs while Pane is hidden and nothing changes, and work that is repeated although nothing changed:

- **Two timer threads per extension runtime thread wake forever, even while Pane is hidden.** The epoch ticker wakes every 10 ms (`crates/pane-core/src/runtime/deadlines.rs`, `TICK` and `tick`) and the watchdog every 100 ms (`runtime/supervisor.rs`, `watchdog`, `WATCH_EVERY`). They do so whether or not a guest call is running. That is at least 110 wake-ups a second, which keeps the CPU out of its deep idle states. It is the main idle cost of an otherwise quiet Pane.
- **Every application icon is extracted again after each start**, by design today ([applications](https://github.com/hoangvu12/pane/blob/main/docs/applications.md), "After each start it re-extracts once…"; `crates/pane-core/src/applications/icons.rs`). For a few hundred applications that is minutes of background work after every sign-in, mostly reproducing the same pictures.
- **Clipboard history is cloned whole on every frame its view draws**, and rewritten whole on every copy:
  - the view calls `Launcher::clipboard_history` per render (`crates/pane/src/features/clipboard_history.rs`), which clones the owner's whole history (`clipboard/history.rs`, `HistoryStore::get`) and then every item's text into records (`launcher/clipboard_view.rs`);
  - each change serialises the entire file as pretty-printed JSON and lists the image folder (`clipboard/history.rs`, `write`).

  With #130's encryption of each item this grows: every write would re-encrypt every item.
- **No measurement says how much Pane costs while hidden.** The resource measurement (#4, `scripts/measure-linux.sh`, [resource measurements](https://github.com/hoangvu12/pane/blob/main/docs/research/resource-measurements.md)) has an `idle-core` phase with Pane visible at root search. It has no phase with Pane hidden, and it does not count wake-ups. Its ceilings are pending.

Root search's per-keystroke costs found by the same read are not part of this specification. Those are providers that are not debounced, an instance dropped when its answer is superseded, re-ranking every row on each answer, and indexed results asked again on every show. They belong to the "Root search like Raycast" specification (#122), whose provider budget and late-answer merging decide how root search asks.

## Solution

- **Measure first.** The resource measurement gains a hidden-idle phase and counts wake-ups per thread, so each change below has numbers before and after.
- **Nothing ticks while no guest runs.** The epoch ticker and the watchdog of a runtime thread sleep while no guest call is in flight on it, and wake when one starts. A running call is timed and watched exactly as today.
- **Icons are extracted when they change.** An icon is extracted again only when the file it is read from changed. For a shortcut, that is the file the shortcut takes its icon from, not only the shortcut.
- **Clipboard history is shared, not copied, and written in proportion to the change.**

## User Stories

1. As a user on a laptop, I want Pane hidden in the tray to use no CPU while nothing happens, so that it does not cost battery.
2. As a user, I want Pane's background work after I sign in to be short, so that my computer is not busy for minutes after every start.
3. As a user with a long clipboard history, I want its view to stay smooth and copying to stay instant, however long the history is.
4. As a maintainer, I want idle cost measured with Pane hidden and wake-ups counted, so that a regression is seen before a user does.
5. As an extension author, I want a computing call still stopped after its limit and a hung runtime thread still replaced, so that saving power does not weaken the guarantees my users rely on.

## Implementation Decisions

### Scope and decision provenance

- **Decided by the user (2026-10-08):** the core app comes before extension features, and the findings of the extension-cost code read are tracked. File-index findings go to #126, root search's to #122, and the rest to this specification.
- **Proposed defaults, delegated:** the measurement's phase lengths and the batching delay for clipboard history writes (below).

### 1. Measurement

- `scripts/measure-linux.sh` (or the `proc_tree.py` sampler) gains a `hidden-idle` phase: Pane hidden after one show, nothing installed beyond the defaults, 60 s. It records whole-tree CPU share and the voluntary context switches of every thread over the phase (from `/proc/<pid>/task/*/status`), named by thread name, so `pane-runtime-epoch` and `pane-runtime-watchdog` are visible. The existing `idle-core` phase gains the same counts.
- `scripts/resource-targets.json` gains the phase. Ceilings stay null until the user confirms numbers, as the file's note says.
- A Windows counterpart (a PowerShell script beside `smoke-windows.ps1`) records the same for a scratch Pane on a scratch data folder. It reads per-thread context switches and process CPU time. It never captures the screen and never touches the user's own Pane data. It runs on the user's machine only with their consent.

### 2. The epoch ticker and the watchdog

- A runtime thread's ticker waits, without a timeout, while no guest call is in flight on that thread. A call starting (any guest call: commands, root results, schedules, services, operations) wakes it. It ticks every 10 ms while a call is in flight, as today. "A last tick after the thread's end", which makes a guest stuck in a call reach its epoch check, is kept.
- The watchdog likewise sleeps while nothing is in flight and the thread is not ending. While a call is in flight it looks every 100 ms, as today, with the same limits: computing at most `COMPUTE_LIMIT`, and a thread making no progress for its limit is given up.
- A continuing service's cycle and a scheduled run are calls. While they run, the ticker runs; between cycles it sleeps.
- Nothing visible changes. The pausing, stopping and unresponsive-call behaviour of [pausing](https://github.com/hoangvu12/pane/blob/main/docs/pausing.md) and [generations](https://github.com/hoangvu12/pane/blob/main/docs/generations.md) stays as documented, and those documents state that the threads sleep while no call runs.

### 3. Application icons

- An icon's fingerprint covers the file the icon is actually read from: for a shortcut, its icon location or target as well as the shortcut; for a packaged app, its manifest's logo asset; for an app bundle, its icon file; for a desktop entry, the themed icon's resolved file.
- After a start, an icon whose fingerprint is unchanged is drawn from the cache and not extracted again. A changed or missing one is extracted, on demand first, as today.
- To catch a change no fingerprint sees, an unchanged icon is extracted again when its cached picture is older than 7 days (proposed), a few at a time at low priority.
- [Applications](https://github.com/hoangvu12/pane/blob/main/docs/applications.md) is updated in place of "After each start it re-extracts once".

### 4. Clipboard history

- The launcher keeps the clipboard history's records for the view behind a change counter, shared (`Arc`, `SharedString`) rather than cloned. A render with no change since the last one clones nothing. The actions panel's reads use the same records.
- Writes are batched: changes within 500 ms (proposed) are written once, and a write is always flushed on a clean quit and before the process ends through the system's session end. Losing a copy made less than that time before a crash is accepted.
- The file is written compactly (not pretty-printed). Images are pruned only when an item holding an image was removed or expired, not on every write.
- With #130's protected items, an item is encrypted once when it is kept and its protected bytes are reused by later writes, never re-encrypted per write.

## Testing Decisions

- A good test checks what a user or a measurement observes, never thread names or the internal call graph, except where the measurement itself names threads.
- **Runtime:** core tests through `Launcher` with the existing samples (prior art: the pausing, stopping, schedules and services suites). A computing guest is still stopped after its limit. A hung runtime thread is still replaced. A schedule and a service still run and are timed. Then, with nothing in flight, a test hook reports the ticker and watchdog asleep, and they are awake again as soon as a call starts.
- **Icons:** core tests with the recording extractor the applications tests use. After a restart over the same cache, an unchanged application is not extracted again. A shortcut whose target changed is. An icon older than the refresh age is extracted again, at low priority.
- **Clipboard history:** tests with the recording clipboard:
  - several copies within the batching delay are written once and all read back after a restart;
  - a clean quit flushes;
  - images are pruned when their item goes;
  - rendering the view twice with no change does not rebuild the records (a test hook or counter).
- **Measurement:** the Linux phase runs in CI's existing measurement job, if one runs it, or on demand. The Windows script runs on the user's machine with their consent. The numbers before and after are recorded in [resource measurements](https://github.com/hoangvu12/pane/blob/main/docs/research/resource-measurements.md).

## Out of Scope

- Root search's per-keystroke work (#122).
- The file index's performance (#126).
- EcoQoS or background priority for the whole process while idle, and resume-after-wake handling (a later item; the research's "Power" gap).
- Ceilings in `resource-targets.json`: proposed after the measurement and confirmed by the user, not set here.
- Any change to what extensions can do, or to the extension API.

## Further Notes

- The ticket order: measurement first, then the ticker and watchdog (measured before and after), with icons and clipboard history independent of both. Clipboard history waits for #130, which changes the same file's format.
- The 10 ms tick and the 100 ms watchdog interval are unchanged while a call runs; only their running while nothing runs is removed.

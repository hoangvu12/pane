# File-index targets (#126): benchmark, volumes, fragments, ignore cache, tiered merges

Five tickets on the file index's cost and scope, one commit per ticket:

- **#183 — the benchmark.** `cargo xtask file-index-bench` reports misses, typed-out prefixes, kind filters and inside-word fragments as their own rows, times on a single-segment index and a multi-segment one with a live memtable, and covers a deep path under ignore files (with and without kept folders). A reduced run with ceilings (`cargo xtask file-index-guard`) guards it in `ci-branch.yml`'s Linux shard 2; `docs/agents/ci.md` says so.
- **#184 — network and removable roots.** A root on a network share or a removable drive is left out by default on every system (a `VolumeKinds` seam, real calls per platform) and included by the File Search page's switch; an included share is reconciled, not watched. Churn counts only paths the index's rules admit, so `node_modules`, ignored and hidden folders never quarantine anything.
- **#185 — the fragment index.** Queries answer through an index of word fragments (trigrams) instead of a full scan of every term, tombstones are looked up by prefix, and a Bloom filter over each segment's keys rules out absent keys; the format version is bumped to 2 and old indexes are rebuilt. A brute-force reference test checks the same entries in the same order across segments, the memory table and tombstones.
- **#186 — the ignore cache.** The scope's ignore rules are kept between batches (`Admitted` memo, forgotten under changed folders), `.gitignore` edits hide and show their files across batches, a new `.git` starts applying its rules, and the user's excluded patterns apply without a restart. The check at Enter shares the cache.
- **#187 — tiered merges and the folder-id table.** Segment merges run on the index's own background thread in tiers of neighbouring segments, off the coordinator thread and off the writer lock while writing; the Windows folder-id table is read once per open and shared between the catch-up and the watch. A merge cut short by closing leaves no file; a crash leaves an unlisted one that is deleted at open, with every change recovered through the write-ahead log.

Follow-ups: `63f1e8ed` routes the file index's merge panic through the diagnostic path that #129 landed (its test forbids raw `eprintln!`s), which was the one integration point left open.

## What was built

- **Fragment index.**
  - `terms::fragments(term)` gives each 3-byte run of a term's word, with the tag in front, as a big-endian `u32`, sorted and deduplicated. Bytes are used, not characters, so this matches the existing byte substring check.
  - **Segments** (`segment.rs`): each term is written before its postings; `fst` values still point at the postings, so `postings_into` and the word-start pass are unchanged. Also written: a `u32` offset per term ordinal (its place in fst order), the fragment lists (count, then ordinal gaps), a fragment table (sorted `u32` fragment and `u32` offset, binary-searched), and the key filter.
  - New `Segment::term(ordinal)` and `Segment::terms_with_fragments(wanted)`. The second decodes the shortest list first and streams the rest against it.
  - **The memory table** gets `term_list` (term by first-seen number) and `fragments: HashMap<u32, Vec<u32>>`.
- **Inside-word pass** (`Source::word_inside`): the matching terms are intersected, each is checked with `holds`, and their postings are appended in dictionary order. Segment ordinals already ascend; memory terms are sorted by bytes. It stops at `SHORT_WORD_ENTRIES` exactly where the scan did. A word under 3 bytes falls back to the scan; this cannot happen today, since `INSIDE_FROM` is 3 characters.
- **Tombstones** (`store::Tombstones`):
  - A `BTreeMap` from prefix to its newest seq, for prefixes ending in a separator (all that `apply` makes). Any other prefix goes in a list that is scanned.
  - A candidate's check looks up the separator positions of its key, between the shortest and longest prefix lengths. It returns at once when `seq >=` the newest tombstone's seq.
  - The flush and merge filters use it too.
- **Key filter.** A Bloom filter per segment over every key, deletions included:
  - 10 bits per key, 7 probes, double hashing, at least 8 bytes.
  - Pane's own hash (`segment::key_hash`), because `std`'s hasher may change between Rust releases.
  - `Segment::find` returns `None` at once when the filter rules the key out. That speeds up `is_current`, `get`, `children`, `recent` and `folder_ids`.
  - The memory table needs no filter: its lookup is a `BTreeMap` already.

## Size on disk (estimate, needs numbers)

Version 1 measured 73 B per entry on the home folder (34.7 MB for 476,017 entries). Version 2 adds:

| Per distinct term | Bytes |
| --- | --- |
| The term stored again (length and bytes) | ≈ 10 (average word ≈ 8 bytes plus tag) |
| Its offset by ordinal | 4 |
| Its fragment postings | ≈ 8–12 (about 6 fragments of 1–2 bytes each) |
| **Total** | **≈ 22–26** |

Other additions:
- the fragment table, 8 B per distinct (tag, trigram), probably 0.4–1.2 MB in all;
- the key filter, 1.25 B per entry.

With roughly 0.6–1.0 distinct terms per entry, that is about 15–28 B more per entry. That gives 88–101 B per entry, about 42–48 MB for the home folder, under the 61.8 MB target. The benchmark's disk row confirms it.

Write-time cost:
- `segment::write` holds a `Vec<(u32, u32)>` of (fragment, ordinal) pairs, 8 B per pair. That is about 20–40 MB at the final merge of a home-sized index.
- It also holds 8 B per entry of key hashes.
- The first index will spend some extra time on fragment sorting and hashing.
- The memory table keeps each term twice and 4 B per (fragment, term).

## Spec ambiguities, resolved

- **The ticket's "results unchanged" vs. the scan's early stop.** Matching terms are visited in dictionary order and stop at the same `SHORT_WORD_ENTRIES` point. With the empty `all` every caller passes, that gives exactly the scan's postings.
- **The key filter** is a Bloom filter rather than a sorted key-hash table: 1.25 B per entry instead of 8.
- **Tombstones** are kept by prefix with the newest seq per prefix. For one prefix this is equivalent to scanning its tombstones, since `covers` is `seq < t.seq`.
- **"An index of the old version is rebuilt"**: the existing test now covers version 1 explicitly.

## For #187 (tiered merges, a shared folder-id table)

- **The format:**
  - `format.rs` `FORMAT_VERSION` (now 2);
  - `segment.rs`: the layout doc at the top, `write_to` and `Segment::open`. The footer is a flat list of `u64` fields: 21 now, `FOOTER = 21 * 8 + 8`, read by `field(n)`.
  - A shared folder-id table can add footer fields after index 20, or a file of its own beside `index.json`. If #185 and #187 ship together, version 2 can carry both; otherwise bump to 3.
- **The merge path** (all in `store.rs`):
  - `FileIndex::compact_locked` (the `Merge` iterator, then `segment::write`), called by `maintain_locked` when there are more than `MAX_SEGMENTS`, and by `Bulk::finish`;
  - `flush_locked` writes the memory table;
  - `Bulk::write_buffer` writes bulk segments.
  - `segment::write` builds the fragment index and key filter from the docs it is given, so a tiered merge that calls it gets them for free.
  - Tombstones are `State::tombstones: Tombstones`, cleared on a full merge. A tiered merge that keeps some segments must keep the tombstones still needed by older segments. It can rebuild the set with `Tombstones::from_iter`.

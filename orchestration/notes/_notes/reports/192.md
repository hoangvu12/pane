## What was built

- **`clipboard/history.rs`:**
  - `State` gains `version` (bumped by every change and by a re-read of the file), `images_went` and `due`. The `Pending` file clones are gone: the file is cloned once per write, not once per change.
  - `HistoryStore::changes()` and `get_counted()` give that count. Both apply expiry first, which counts as a change.
  - `queue()` arms a batch `WRITE_DELAY` (500 ms) after the first unwritten change. The existing expiry thread (`keep_expiring`) writes the batch when it is due (`write_due`), so there is no new thread. A store whose thread is not running writes at once, as in unit tests and `ExtensionData` tests.
  - Captures and expiry writes are batched.
  - Command changes (`write_staged`) and `remove` write synchronously and take the waiting batch with them.
  - `counts_now` flushes first, because it reads the file.
  - `Drop` flushes.
  - `flush()` is public.
  - `write_now` writes the current state if `changes > written`, compactly (`serde_json::to_string`). It prunes only if an image (owner, digest) present before a change is gone after it (`State::change` compares the two sets).
  - `prune_images` keeps PNGs named by either the snapshot just written or the in-memory state. This closes a race where a capture added an image item after the write's snapshot.
  - The orphan prune now runs only from the public `sweep()`, at start and in `with_clock`, not on every loop of the thread.
  - `seal()` reports whether it encrypted now, and per-store counters give `writes()` and `items_protected()` (test hooks).
- **Launcher:**
  - `quit_cleanly` flushes the history first. It is reached by the tray Quit, window close, and GPUI's quit hook, which runs for `WM_ENDSESSION` and macOS termination per #133.
  - New hooks, `cfg(any(test, debug_assertions))` and `doc(hidden)`: `wait_for_clipboard_writes`, `clipboard_history_writes`, `clipboard_items_protected`, `clipboard_records_made`.
- **`clipboard_view.rs`:**
  - `ClipboardHistoryView::records` is `Arc<[ClipboardRecord]>`, and `ClipboardRecord::text` is `Arc<str>`.
  - The launcher `State` keeps a `Projected` (owner, change count, records and choices). `clipboard_history()` calls `store.changes()` and reuses the shared records when the count matches, otherwise rebuilds off the launcher lock.
  - The Actions panel calls the same function, so it reads the same records.
- **Pane view (`features/clipboard_history.rs`):**
  - The `ClipFrame` keeps a `FrameKey` (the records `Arc` by `ptr_eq`, `ClipboardBrowse`, the minute, the UTC offset) and is reused while that key holds.
  - Rows hold `SharedString`s. The preview's text is `SharedString::from(Arc<str>)`.
  - The one-second watcher compares the records `Arc` instead of cloning ids.

## Look here first when compiling

- **Borrows:**
  - `State::change`: `self.file.as_mut()` alongside writes to `self.images_went` (disjoint fields).
  - `write_latest`: `match &outcome` while holding the `written` guard.
  - The render's `state.frame.clone().filter(|frame| ... &state.browse ...)` closure, and `chosen` and `selected` borrowing the frame `Rc` and `history`.
- **Inference:** `Vec::<ClipboardRecord>::new().into()` and `.collect()` into `Arc<[ClipboardRecord]>`; `SharedString` from `Cow<str>`, `&str` and `Arc<str>` (all read in gpui_shared_string).
- **Lints:** `dead_code` on the `WakeState::writes` field (allowed outside test and debug, like `swept`) and on the atomics read only by test-gated getters (I believe `fetch_add` counts as a use).
- **Formatting:** rustfmt was not run. The likeliest diffs are the closure in the window test's `made`, `kept_on_disk` chains, and the render's `kept` filter chain.
- **Timing assumptions in tests:**
  - "One write for the burst" assumes three in-memory copies take less than 500 ms.
  - `a_clean_quit_writes_the_copies_that_wait` cannot tell a quit flush from a thread write that happened first. It checks only that the copy is on disk right after quit.
- **Window test:** it assumes `settle` draws a frame after each key, and that nothing else bumps the history count. The clock is manual, so nothing expires.
- **A #130 bug fixed in passing:** #130's unit tests reopened the store with `HistoryStore::open` (system clock) and read items copied at `DAY`, which the system clock expires. They now reopen with `store_at(dir, DAY)`. These are `an_item_is_written_…` and `an_item_that_cannot_be_read_…`.
- **A latent issue I did not fix:** `Launcher::with_packages` sweeps with the system clock before `with_clock`. `clipboard_view.rs` tests that restart (`a_fresh_data_folder_records_the_first_copy_with_no_turn_on`) copy at a fixed 2026-10-05 clock, so they would lose their items after 2026-10-12 on the CI's real date. My new restart tests move the manual clock a year ahead first (`ahead_of_the_system`).

## Spec ambiguities resolved

- **Which writes are batched:** copies (`capture`) and expiry writes. A command's change (delete, clear, pause or resume, retention, disabled applications, the view's operations) and an uninstall's `remove` still write before returning, with the waiting batch, because their callers report a write failure. The guest contract's "on disk when the call returns" also stays true for them. This is documented.
- **"Pin":** clipboard history has no pin, so the counter is bumped by keep, delete, choice changes and expiry.
- **`SharedString`:** pane-core has no gpui, so the core shares `Arc<[ClipboardRecord]>` and `Arc<str>` text, and the window converts to `SharedString` cheaply.
- **Session end:** this relies on GPUI's quit hooks (#133). On Linux, and for signals on macOS, only the marker is removed, so up to 500 ms of copies can be lost there. This is documented.
- **The delay window is fixed from the first unwritten change, not sliding**, so a constant stream of copies is still written at least every 500 ms.
- **Measurements:** none were requested for this item, and none were taken.

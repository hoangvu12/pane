## The benchmark was not run; the code read was checked instead

I checked the ticket's reading against `08ec288c`. It holds, with one caveat about the benchmark.

- **The folder-id table was read twice per open on Windows, and needlessly the second time.**
  - `FileIndex::folder_ids` (store.rs) visits every entry of every source and runs `is_current` on each folder.
  - `changes/ntfs.rs:73` read it unconditionally, even when no volume had usable records.
  - `indexer.rs` `indexed_folders` (called at the end of `catch_up`) read it again for the watch setup. NTFS's `watch` ignores those folders (`_folders`), and so does macOS's, so that read was wasted.
  - A third read followed every first walk (`do_walks`). It was also unused on Windows and macOS.
- **Merges ran on the coordinator thread.**
  - `apply` → `maintain_locked` → `compact_locked` merged every segment into one once there were more than `MAX_SEGMENTS` (8).
  - It held the writer lock for the whole rewrite, so change handling waited. Queries did not; they only read `state`.
- **Caveat: the benchmark's catch-up row measures neither cost.**
  - Its `catch_up` calls `folder_ids()` once and never goes through the coordinator or the watch setup.
  - Its 10,000 puts stay in the memory table (no flush, so no merge).
  - So the 1.64 s comes from the journal read, one folder-id read, `Names` (one `OpenFileById` per unnamed record), `catch_up_changes` (an `Entry::read` and `Scope::admits` per path, which is #186's subject), `missing_from` and `apply`.
  - This ticket saves the real start one full table read, and any merge stall. It may not move that row much. The benchmark has to say where the 1.64 s goes.

## What was built

- **`store.rs`**
  - `FileIndex` now holds `state`, `writer` and a new `merges` in `Arc`s, shared with a `Merger` thread. The thread is spawned in `open` and named `pane-file-index-merge`.
  - The thread calls `lower_current_thread()`, the walker's and coordinator's helper.
  - `Drop` closes it and joins it before the lock file is let go.
  - **Policy (`tier_to_merge`):**
    - 4 neighbouring segments whose largest is at most 4× the smallest, sizes floored at 4,096 entries; the smallest such run is merged.
    - With more than 8 segments, the smallest run of 4 neighbours, whatever their sizes.
    - Only neighbours are merged, so each segment stays newer than every older one (`is_current` relies on that).
  - **Locks:**
    - `merges.merging` is held for a whole merge. It is always taken before the writer.
    - The writer is held only to allocate the file id and to swap the segment in and save the manifest, never while writing.
    - `bulk()` and `compact()` take `merging` first, so a first walk and a full compaction never overlap a background merge.
    - `maintain_locked` no longer compacts; `flush_locked` signals the merger.
  - **Tombstones:**
    - `write_merged` drops what the snapshot of tombstones covers.
    - Deletions and the run's carried tombstones are dropped only when the run starts at the oldest segment; otherwise the merged segment carries them on.
    - After a swap, `state.tombstones` is rebuilt from the segments plus `unflushed_tombstones`.
    - `flush_locked` now keeps the tombstones it is writing in `unflushed_tombstones` until its segment is pushed, so a rebuild in between keeps them.
  - **A merge cut short** (closing) deletes its file. A crash leaves the file unlisted, and `load` already deletes unlisted segments.
  - `pub fn wait_for_merges()` was added for tests and the benchmark. The cfg(test) helpers are `hold_merges`, `pause_merges_before_swap`, `wait_until_merge_paused` and `folder_id_reads`.
- **`changes.rs`**
  - New `pub struct FolderIds<'a>`, re-exported from `file_index`. It reads the table lazily (`ids()`), keeps it current after the catch-up's changes are applied (`apply`), and lists the folders shallowest first (`folders`).
  - `ChangeSource::catch_up` gains `folders: &mut FolderIds<'_>`.
  - New default method `watches_folders()` returns false; Linux overrides it to true.
- **`ntfs.rs`** reads `folders.ids()` only when a volume's records come back.
- **`indexer.rs`**, kept small:
  - `catch_up` builds one `FolderIds`, passes it to the source, applies the caught-up changes to it, and gives the watch folders only if `watches_folders()`.
  - After a first walk it reads the folders only for such a source.
- **Format.** The table is not persisted and `FORMAT_VERSION` stays 2; neither the manifest nor the segment layout changed.

- **`dead_code` in non-test builds.** `Turns::paused` is only written outside tests, so it has `#[cfg_attr(not(test), allow(dead_code))]`. `held` and `pause_before_swap` are read in non-test code.

  - the multi-line `let … else` in `replace_run`;
  - the `pub use changes::{…}` wrap.

  - The merge tests rely on `hold_merges` / `pause_merges_before_swap` and a 20 s timeout in `wait_until_merge_paused`.
  - The reference test holds merges for its first part; after reopening it lets them run concurrently with queries.
  - The expected segment counts (2 and 3 after the merge) and the run picked (start 0 for 3 flushed batches, start 1 for 4) come from my hand count of the fixture's sizes. All are under 4,096, so all are "similar".
- **Copying a live index folder on Windows** (restart test) uses `fs::read`/`fs::write`, relying on std's default share mode to read the open WAL and the mapped segments.
- **The Windows native test** assumes the runner's temp volume has a journal. It accepts 0 reads otherwise.
- **`Drop` for `FileIndex` now joins the merger.** A merge under way stops reading at once, but `segment::write` finishes the cut-short file before it is deleted. If the last `Arc<FileIndex>` drops on a UI thread mid-merge, that thread waits that long. `Indexer::stop_and_wait` already waits on the caller in the same way.

## Spec ambiguities, resolved

- **"Share it between catch-up and the watch setup".**
  - The table is lazy and per open. On Windows and macOS the watch never needs it, so it is read once (Windows: by the catch-up, only when records come back) or not at all (macOS). Linux reads it once, for its watches.
  - `FolderIds::apply` keeps a table read by the catch-up current for a watch that wants it. No system needs both today; the seam test covers the combination.
- **Persisting the table.** Not done, as told. The docs say it waits for the benchmark.
- **The first walk's final merge** stays synchronous (`Bulk::finish`), so the first-index and size rows still mean what they meant. It runs with no background merge running.
- **"Never the window's or the runtime's"**: the merge thread is the index's own and runs at background priority.
- **Catch-up stays at start**, unchanged.

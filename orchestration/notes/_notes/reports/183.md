## What was built

- **Query set** (`query_set`, `texts`, `run_query`).
  - The sample is sorted first. Before #183 it was in the order the walk's threads found it, so the set was not actually fixed between runs.
  - Each kind gets about `--queries / 11` queries. A typed-out name counts each keystroke, and its keystrokes run one after another. The kinds take turns.
  - Misses come from a seeded SplitMix64: a `q`, then one of `xzjkvw`, then consonants, 3 to 8 letters in all. Each one is checked untimed to find nothing, on an index that is opened and closed before the timed open. That keeps "first pass after opening" honest.
  - The Document filter copies `Indexer::search`'s category loop: ask for 500, keep documents, ask for 4× while fewer than 20 are kept, up to 20,000. The Folder filter is `Query.kind`.
- **Index shape** (`stream_changes`).
  - After the re-index rows and catch-up, the bench removes what the changes put in a generated tree, then calls `compact()`.
  - It then applies 5 batches of `entries/50` changes each, clamped to 500..10,000. All batches but the last are followed by `flush()`. That leaves 5 segments and one batch in the memtable, below `MAX_SEGMENTS` (8) and `MEMORY_TABLE_ENTRIES` (65,536).
  - Each batch has: new files beside sampled entries (60%), new versions of sampled entries (30%), and removal of files the previous batch added (10%). It also adds a folder with 10 files and `RemoveUnder`s the previous batch's folder, which leaves tombstones.
  - Only the index changes, never the disk.
- **Re-index** (`reindex`, `deep_folder`).
  - Both rows now time the steps of `Indexer::look_at`: `get`, `Entry::read`, `Scope::admits` with a fresh `Admitted` (which reads the ignore files on the way), `apply`, then a search that finds it. Before #183 the row skipped `get` and `admits`, so it is not directly comparable with the #174 number.
  - The deep folder is picked from the parents of sampled entries, among the 1,000 deepest. The ranking is: has an ignore-file folder on the way, then deepest, then most such folders. The candidate must also admit the probe file.
  - The deep file is written in the changes folder and indexed under the deep folder's path, then removed again, so nothing is written to the home folder or the tree.
- **Guard.**
  - `--guard` checks these ceilings (`GUARD_*` constants): first index 180 s; 400 B per entry; p95 of every kind and of all kinds on both shapes (warm) 2.5 s; each re-index p95 2.5 s. It exits 1 when any is exceeded.
  - `cargo xtask file-index-guard` runs `cargo build --locked --workspace --examples` (dev profile, reusing the test build), then runs `target/debug/examples/file_index_bench --generate 20000 --runs 1 --queries 550 --foreground --guard`.
  - `ci-branch.yml` runs it in Linux shard 2/3 after the tests.

## Unsure and unconfirmed (look here first when compiling)

- **The ceilings are guesses.** The dev-profile numbers for a 20,000-entry tree on a CI runner were never measured. 2.5 s per query p95 is meant to be far above the expected value. The worst cases should be misses and the Document filter in debug, which can re-ask up to 20,000. Tighten the ceilings from the first CI log; the guard prints the whole report.
- **`cargo build --workspace --examples` reusing nextest's build.** I expect resolver-2 feature unification to match `cargo nextest run --workspace`, and nextest's `cargo test --no-run` to have built the example already. If it rebuilds dependencies, the shard gets slower but stays correct. If `CARGO_TARGET_DIR` or `CARGO_BUILD_TARGET_DIR` were set differently, the binary path could be wrong; only `CARGO_TARGET_DIR` is honoured.
- **rustfmt.**
  - The `use pane_core::file_index::{…}` first line is exactly 100 columns. I believe rustfmt allows that.
  - Some `println!`s have string literals over 100 columns. rustfmt leaves those as written, as it did with the existing ones.
- **Clippy 1.98.** I avoided `x.max(const)` on constants (`unnecessary_min_or_max`) and `% n == 0`. A new lint may still flag something.
- **Coercions.** Closure arguments use `.as_slice()` and `as_path()` explicitly.
- **Deep folder in a tiny tree.** In the 20,000-entry generated tree, Git repositories sit in every 100th folder, and the deepest sampled folders under folders 99, 199, … should have one on the way. If none qualifies, the row still prints and says "0 … with ignore files".

## Unsure, look here first when compiling

- **`Session::Current` and the moves in `run`'s match.** `job.id` is moved in arms that `return`, and the code after the match uses it again. I expect the borrow checker to accept this.
- **COM in `picture_files`.** It calls `Com::new()` per fingerprint on the worker thread, and `extract` then does its own. I believe CoInitializeEx/CoUninitialize pairs fine in sequence. The cost is one COM init and one `.lnk` load per listed shortcut per start.
- **Shortcuts without an icon location.** I assume `GetIconLocation` returns an empty string for a WScript-made shortcut with none set. The test's `before.contains("tool.exe")` holds either way.
- **macOS adapter test.** It now asserts that Calculator's fingerprint contains `/Resources/`. This assumes Calculator's `Info.plist` has `CFBundleIconFile` or `CFBundleIconName`.
- **rustfmt widths.** I formatted by hand against the `fn_call_width` and `chain_width` heuristics. The borderline spots are the `info_plist(...)` calls and the asserts in the `icons.rs` tests, and the `fingerprint` helper in the adapter test.
- **`IconCache::with_clock`.** It is `cfg(any(test, debug_assertions))`, like `Cached::with_clock`, so the integration tests depend on debug assertions, as `application_cache.rs` already does.
- **Batches that extract nothing.** They no longer call `changed()` or rest `BACKGROUND_REST`. I believe nothing depended on a redraw notice per batch, since the index load still notifies once.

## Spec ambiguities resolved

- **Fingerprint format.** It is the source's fingerprint followed by each picture file's fingerprint, joined by a blank line. A picture file that cannot be read counts by its path, so its appearing changes the fingerprint. Because the format changed, every cached icon is re-extracted once after the upgrade. That happens anyway, because the old index's pictures read as old.
- **What "the file the picture is read from" covers.** Beyond the ticket's four cases, it also covers a `.url`'s `IconFile` and an `.appref-ms`'s deployed program, the files `extract` actually reads. For a packaged app it covers both the dark and the light logo files.
- **The age clock.** The clock is wall time in ms, and 0 means "from an earlier Pane". A recorded time more than `REFRESH_AGE` in the future also counts as old, so a badly wrong clock cannot pin a picture as young forever.
- **When the age is checked.** An urgent (on-screen) job whose fingerprint is unchanged and whose picture is young is marked done for the start. If the picture is old, it is drawn from the cache and queued for the background, as before.
- **Unreadable fingerprints.** A `None` fingerprint is taken as unchanged, so the icon is re-extracted only once its picture is old. The trait doc now says so.

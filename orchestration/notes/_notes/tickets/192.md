#192 [OPEN] Share clipboard history with its view instead of cloning it per frame, and batch its writes
## Parent

https://github.com/hoangvu12/pane/issues/188

## What to build

Section 4 of the parent, "Clipboard history": the clipboard history view and the actions panel read shared records instead of cloning the whole history on each frame, and the history file is written once per burst of changes, compactly, with images pruned only when an image item goes. Size M.

Today (104a5dac):

- The view calls `launcher.clipboard_history()` in its render (`crates/pane/src/features/clipboard_history.rs` ~670, and five more call sites there, plus `actions_panel.rs` ~617 and ~752).
- `HistoryStore::get` (`crates/pane-core/src/clipboard/history.rs` ~607-621) clones the owner's whole `PackageHistory`, and may trigger an expiry write.
- `Launcher::clipboard_history` (`launcher/clipboard_view.rs` ~608-664) clones every item's text and files into records.
- `HistoryStore::write` (`clipboard/history.rs` ~878-891) pretty-prints the whole file, writes it atomically, then lists the image folder (`prune_images`).

What to build:

- The launcher keeps the view's records behind a change counter that the store bumps on each keep, delete, pin and expiry. The records are shared (`Arc`, `SharedString`), and a render with no change clones nothing.
- Writes are batched for 500 ms (proposed). A clean quit flushes. Expiry writes are batched the same way.
- Compact JSON. `prune_images` runs only when an item with an image was removed or expired.
- With #130's protection, an item is encrypted once when kept and its protected bytes are reused by later writes.

## Acceptance criteria

- [ ] Tests with the recording clipboard (prior art: the clipboard history suites, and #130's):
  - several copies inside the batching delay give one write, and all read back after a restart;
  - a clean quit flushes a pending write;
  - an image item's file is pruned when the item is deleted or expires, and not otherwise;
  - on Windows, items stay protected and are not re-encrypted per write (a test hook counts protector calls).
- [ ] A window test (real key events) renders the clipboard history view twice with no change, and the records are not rebuilt (a counter or test hook). Search, pin and delete in the view still work.
- [ ] `docs/clipboard-history.md` (or the document that owns the history file) states the batching and that a copy made less than the delay before a crash can be lost.
- [ ] CI: the branch tier is green, and a `ci-fast` verify run is green. No release matrix.

## Blocked by

- #130 (it changes the history file's format and protects each item; build on it)

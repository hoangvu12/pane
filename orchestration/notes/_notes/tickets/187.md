#187 [OPEN] Catch up 10,000 changes within 1 s: build the folder-id table once, and merge segments in tiers off the coordinator thread
## Parent

https://github.com/hoangvu12/pane/issues/126

## What to build

Catch-up after 10,000 changes takes under 1 s on Windows, the parent's target; it is 1.64 s today ([`docs/evidence/files-174`](https://github.com/hoangvu12/pane/tree/main/docs/evidence/files-174)). Applying a large batch never stalls change handling behind a whole-index rewrite. Size M.

Where the time goes (read on 104a5dac; confirm with the benchmark first):

- **`FileIndex::folder_ids()` runs twice at open on Windows.** It visits every entry of every source and checks each folder (`crates/pane-core/src/file_index/store.rs` ~887-909). It is called by the NTFS catch-up (`changes/ntfs.rs` ~73) and again by `indexed_folders` (`indexer.rs` ~1675) for the watch setup.
- **Merges run on the coordinator thread.** Past `MAX_SEGMENTS` (8, `store.rs` ~40), `maintain_locked` (~954-960) merges every segment into one (`compact_locked`, ~1019-1060) on the coordinator thread, from `apply` (~628). Change handling waits for a full rewrite.

What to build:

- Compute the folder-id table once per open and share it between catch-up and the watch setup. If measurement shows it is still too slow, persist it with the segments; that is a format change, landed in one version bump with #185's.
- Merge in tiers (a few similar-sized segments at a time) on a background-priority thread of the index's own, never the window's or the runtime's. The coordinator keeps applying changes while a merge runs, and queries keep working throughout. Tombstones are dropped only by a merge that covers every segment they could hide, as today.
- Catch-up stays at start, as the parent's "Catching up and watching" and `docs/files.md` (~110-114) decide. Only the walks wait for the first show; this ticket does not move it.

## Acceptance criteria

- [ ] Tests:
  - a merge running while changes arrive loses none of them;
  - a query during a merge returns current results;
  - a restart in the middle of a merge leaves a readable index with every change, through the write-ahead log.
  
  Prior art: the store's and indexer's unit tests.
- [ ] On Windows, the folder-id table is built once per open. A test checks it, through a counter or the seam.
- [ ] The benchmark's catch-up after 10,000 changes is under 1 s on the user's machine, and the query p95 with changes arriving is reported. Numbers go in the results comment. **Ask the user before running the benchmark there; the machine is also used for games.** macOS's catch-up is not measured here: record it as not run.
- [ ] `docs/files.md` describes the tiered background merges.
- [ ] CI: the branch tier is green, and a `ci-fast` verify run is green. No release matrix.

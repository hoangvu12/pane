#185 [OPEN] Answer file queries within 10 ms at the 95th percentile, through an index of word fragments and cheaper currency checks
## Parent

https://github.com/hoangvu12/pane/issues/126

## What to build

A file query answers within the parent's target, under 10 ms at the 95th percentile in the host, on the benchmark's full query set (misses and typed-out prefixes included). Today it is 57 ms on the user's home folder ([`docs/evidence/files-174`](https://github.com/hoangvu12/pane/tree/main/docs/evidence/files-174)). Results stay the same; only the time changes. Size M-L.

Where the time goes (read on 104a5dac; confirm with the benchmark from the blocker before changing anything):

- **The inside-word pass.** `FileIndex::search` (`crates/pane-core/src/file_index/store.rs` ~760-780) runs `matching(..., inside = true)` whenever a word of 3+ letters is present and the word-start pass found fewer entries than asked for. `Source::word_inside` (~259-298) then walks every NAME and FOLDER term of every segment and the memtable, running a substring search on each. It stops only at `SHORT_WORD_ENTRIES` postings. A query with no match reads the whole term dictionary for each word, on every keystroke.
- **Checking a candidate is current.** `State::is_current` (~374-385) scans every tombstone linearly, then calls `find(key)` in every newer source, for each candidate.

Direction, not prescription (the implementer may choose otherwise with measurements):

- Give each segment, and the memtable, a side index of 3-byte fragments of its NAME and FOLDER terms, mapping each fragment to term ordinals. The inside-word pass then intersects the word's fragments and checks only those terms, never the whole dictionary. This changes the segment format: bump the index format version, which already rebuilds an index of another version (`format.rs`). Keep the bytes per entry well under the parent's 61.8 MB target; the size on disk is reported by the benchmark.
- Keep tombstones sorted by prefix so a candidate's check is a lookup, not a scan. Give each segment a cheap key filter (a Bloom filter or a sorted key-hash table) so `find` in a newer source is skipped when the key cannot be there.

Matching and ranking are unchanged: the parent's "Matching and ranking" rules, case and accent folding (`text.rs`), the word-start pass first, and the same scores.

## Acceptance criteria

- [ ] A test compares `search` against a brute-force reference over a fixture index with several segments, a memtable and tombstones. For a fixed set of queries (prefixes, inside-word fragments, misses, accents and case), the same entries come back in the same order as before the change.
- [ ] The index format version is bumped, and an index of the old version is rebuilt (the existing format-change test covers it, or one is added).
- [ ] The benchmark's overall query p95 is under 10 ms on the generated 450,000-entry tree on the user's machine, and the home folder's is reported. The size on disk stays under 61.8 MB. Numbers go in the results comment, beside the baseline from the blocker. **Ask the user before running the benchmark on their machine; it is also used for games.**
- [ ] `docs/files.md` "The file index" describes the fragment index and the new format version.
- [ ] CI: the branch tier is green, and a `ci-fast` verify run is green (the file index's unit tests on Windows; macOS compiles). No release matrix.

#130 [OPEN] Protect local credentials and clipboard history on disk with DPAPI on Windows
## Parent

https://github.com/hoangvu12/pane/issues/129

## What to build

On Windows, local credentials and clipboard history are encrypted on disk for the current Windows user, so a copy of Pane's data folder (a backup, a synced profile, an offline disk read) no longer hands over every token or copied secret. `credentials.get` and `credentials.set` keep their interface and no component is rebuilt. No prompt, no extra service.

- **The protector.** Extension data gains one credential protector per system, between the values in memory and the file. Values stay plain in memory while Pane runs. On Windows each value is protected with DPAPI in the current user's scope, with fixed Pane-specific entropy and the flag that forbids any prompt. Only values are protected: package identities and key names stay readable, so Clear cache, uninstall, deleting retained data and the counts on Manage extensions and the uninstall confirmation keep working without decrypting anything. The file keeps its protected DACL.
- **Format version 2.** The local credentials file moves to version 2, in which each value records how it is protected. Other kinds of extension data stay at version 1. At start on Windows, a version-1 file is converted to version 2 in one atomic write. If that write fails, Pane keeps reading the version-1 file and tries again at the next start; no value is lost. An older Pane refuses a version-2 file, as it refuses any other version, and never overwrites it.
- **A value that cannot be decrypted** (an administrator reset the Windows password, the folder came from another user or computer, the bytes were damaged) is explained, never dropped or regenerated. `credentials.get` returns an error the extension can turn into "sign in again": "Pane cannot read this credential on this computer: Windows could not decrypt it (<reason>). Sign in again." `credentials.set` replaces it. Manage extensions reports it, for example "keeps 2 credentials, 1 unreadable". Other values of the same extension still read.
- **Clipboard history on Windows** gets the same protector: each item's content is encrypted, the file moves to a new format version converted at start in one atomic write, and an item that cannot be decrypted is explained and left in place.
- **macOS and Linux are unchanged:** the user-only file (mode 0600), and the documents say so. The macOS Keychain slice (waits for signing) and the Linux Secret Service slice are later, flagged slices of #129, not this ticket.
- **What it does not protect against:** programs running as the same user can call DPAPI too; the data policy's "lifecycle behavior, not secret isolation from trusted code" stands.
- **Out of this ticket:** the Windows Credential Manager, any change to the credentials interface, encrypting the other kinds of extension data.

## Acceptance criteria

Tests go through the `Launcher` public interface, beside the existing Clear cache and uninstall tests, using each language's settings sample, which keeps a token.

- [ ] Windows: a token saved by an extension reads back unchanged, and the credentials file's bytes do not contain the token's text.
- [ ] Windows: a version-1 credentials file is converted to version 2 at start, and its tokens still read back.
- [ ] Windows: a conversion whose write fails leaves the version-1 file readable, with every token, and the conversion is tried again at the next start.
- [ ] Windows: a value whose protected bytes are damaged gives the extension the explaining error from `credentials.get` while the extension's other values still read; `credentials.set` replaces it; Pane never deletes or replaces it on its own.
- [ ] Windows: Manage extensions counts an unreadable credential as such ("… 1 unreadable").
- [ ] All systems: Clear cache, uninstall and deleting retained data remove credentials, and the counts on Manage extensions and the uninstall confirmation are unchanged, without decrypting anything.
- [ ] All systems: a Pane reading a credentials file of a version it does not know refuses it and does not overwrite it.
- [ ] Windows, with a recording clipboard as the existing clipboard history tests use: a kept item reads back, the history file holds no plain text of it, an earlier history file is converted at start with every item kept, and a damaged item is explained while the others still read.
- [ ] macOS and Linux: the existing credential and clipboard history tests stay green with no change in behaviour.
- [ ] The extension data document, the credentials interface's doc comment and the decision index (replacing "local credentials are plain text") state the protection per system and what it does not protect against.
- [ ] CI: the branch tier is green, and a `ci-fast` verify run is green, which runs the Windows tests above and compiles the macOS leg. No release-matrix run is needed.

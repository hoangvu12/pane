Results, per acceptance criterion (all ran green in the verify run [37898374301](https://github.com/pane-app/pane/actions/runs/37898374301), Windows and Linux shards; its only red is the known macOS pasteboard flake #231):

- Tests with the recording clipboard, in `crates/pane-core/tests/clipboard_view.rs` and `history.rs`:
  - several copies inside the batching delay give one write (a write-counter hook; compact JSON) and all read back after a restart — `several_copies_within_the_delay_are_written_once_and_read_back_after_a_restart`, `a_burst_of_copies_is_written_once_and_a_flush_writes_what_waits`;
  - a clean quit flushes a pending write — `a_clean_quit_writes_the_copies_that_wait` (`Launcher::quit_cleanly` writes the batch first; the tray's Quit, window close and GPUI's quit hook — `WM_ENDSESSION`, macOS termination — reach it);
  - an image item's PNG is pruned only when the item goes (deleted or expired), and a stray PNG that no item names survives — `an_images_png_is_pruned_only_when_an_image_item_goes`, `images_are_pruned_only_when_an_image_item_goes`;
  - on Windows items stay protected and are not re-encrypted per write — `kept_items_stay_protected_and_are_encrypted_once` and `an_item_is_written_as_this_system_protects_it_and_encrypted_once` (the per-store `items_protected()` counter; `seal()` reports whether it encrypted now).
- A window test with real key events renders the clipboard history view twice with no change and the records are not rebuilt (`Launcher::clipboard_records_made()` unchanged), while typing filters, Escape clears, a copy and a Ctrl+D delete each make the records exactly once more — `window.rs::clipboard_split::drawing_again_with_nothing_changed_makes_no_records`.
- `docs/clipboard-history.md` states the batching (500 ms from the first unwritten change, which changes still write at once, what a clean quit and session end do) and that a copy made less than the delay before a crash can be lost; `docs/pausing.md` and the decision index's #35 amendment say the same.

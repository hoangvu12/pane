## 6. Reload / update / development-mode reload (ADR 0004 today)

- `crates/pane-core/src/launcher/reload.rs`: `Attempt::Reload | Retry`; stage 1 re-reads and checks as an install (nothing changes on failure); stage 2 replaces the managed copy, stops the old instances (an open command closes), starts each command (asks its view); a start failure pauses the package, the old code is not restored. **"A command of it that is open closes; its state is not carried over"** — ADR 0004's "explicit extension support" is not implemented; #159 defines it. `Reload::staged` is the development-build path.
- `crates/pane-core/src/launcher/updates.rs`: clock-driven updater thread (`updates.json` controls); a newer version is fetched, checked as an install, staged; **applied only at the safe boundary — no screen of the package on display and no user call running (`Runtime::busy`)** — "an automatic update never applies while a screen is on display" already holds. Applying = a replacement like a reload (identity, data, disabled state, hotkeys, aliases kept).
- Development mode: `crates/pane-core/src/launcher/developing.rs` (launcher host: `Development`, diagnostics in `Screen::BuildDetails`) + `crates/pane-build/src/session.rs` (`Prepared::new` watches the source folder with `notify::recommended_watcher` — `watch()` ~382, the native watcher the spec's folder watchers reuse; builds into a staging folder; hand-over via `Host::claim` → `Reload::staged`; obsolete builds; `MAX_OBSOLETE`).

## Surprises and naming notes

1. The spec's "Rust pane-guest crate" is `guests/pane-extension` (crate `pane-extension`, module `pane_extension`); the JS/TS SDK is `@pane-app/extension` at `guests/js`.
2. No capability/waiting code exists on the branch; ADR 0041 + glossary + ADR amendments are merged, so code starts from zero.
3. #136 is fully merged (undo list + concurrent runtime), satisfying #158's largest blocker; its ticket also lists #137/#138/#139/#143 — several are visibly landed (Actions panel `crates/pane/src/features/actions_panel.rs`, tree `ActionKind::Callback`, icons), but verify each before assuming.
4. Reason kinds: `Unavailable { OnThisSystem, Paused }` — waiting is a third variant. Note `QuickSlot.unavailable` is a plain `Option<String>`, not the enum (existing inconsistency to keep or fix).
5. `State::runs` (enabled && !paused) gates schedules/services/results asking, while root-row listing filters `enabled` and adds `Unavailable::Paused` — two distinct seams for waiting.
6. WIT error kinds include `incompatible` (version mismatch/cannot run), which the spec's capability error list omits; capabilities reuse it.
7. `ManifestJson` ignores unknown top-level fields; new fields use `#[serde(default)]` + `deny_unknown_fields` sub-structs; validation errors are `PackageError::InvalidManifest(String)`.
8. `run-operation` takes the operation name as a plain string — qualified capability operation names need no guest-side change, only routing.
9. The updater already refuses to apply while a screen is on display, so #159's reopen-screen work only concerns Reload, dev-mode reload and user updates.
10. House-record pattern (`launcher/choices.rs`) is the template for #154's provider-choice record; restart persistence is tested by building a new `Launcher` on the same data folder.
11. The launcher window has no extensions screen of its own — "Manage Extensions" opens Settings (ADR 0043); core extensions screens exist for tests (`Launcher::manage_extensions`).

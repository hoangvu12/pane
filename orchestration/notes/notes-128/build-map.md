**`build()` steps** (pane_js.py:~380):
1. Reads `package.json`, requires `main` entry naming the command module.
2. **Staging copy**: `CACHE/work/<pkgname>-<sha8 of path>/` holding `js/` (copy of `guests/js`, so the samples' `devDependencies: {"@pane-app/extension": "file:../js"}` resolves in cache, never in the source tree) and `<pkgname>/` (copytree of the package, `node_modules`/`.git` skipped). `npm ci --ignore-scripts --no-audit --no-fund` into the staged copy when `package-lock.json` hash changed (marker `node_modules/.pane-lock-sha256`).
3. **Type-check**: if `tsconfig.json` exists, `node <toolchain>/node_modules/typescript/bin/tsc -p <staged>` run *from the staged copy* so errors name the author's paths (`src/index.ts(3,7): error ...`).
4. **Adapter entry** `adapted_entry()` (pane_js.py:~470): writes `pane-entry.mjs` importing `console.js` first, then `* as extension from <entry>`, `adaptCommand`/`adaptProvider` from `guests/js/adapt.js`; re-exports entry, wraps `command` and each provider named by the package.json `"pane"` options (`ADAPTED_PROVIDERS`: rootResults→`rootResults/resultsFor`, indexedResults→`indexedResults/results`, operations→`publishedOperations/runOperation`, search→`commandSearch/search`, service→`service/runCycle`).
5. **Bundle**: `node tools/componentize-js/bundle.mjs <tool node_modules> <pane-entry.mjs> <bundle.mjs>` — esbuild `bundle:true, format:esm, platform:neutral, target:es2020, external:["wasi:*","pane:*"], mainFields:["module","main"]`.
6. **World choice by bundle content**: `uses_http(bundle)` regex-matches `wasi:http/` imports; `uses_programs(bundle)` matches `pane:extension/programs@`. `command_world(options, http, programs)` writes `wit/command.wit`: `package pane:js-guest@0.1.0; world js-command { include js-extension; import <…imports…>; export <…exports…> }`. `EXPORT_OPTIONS`/`IMPORT_OPTIONS` (pane_js.py top) map `"pane"` package.json keys → interfaces (`rootResults`,`indexedResults`,`operations`,`search`,`service` exported; `files`,`fileIndex`,`clipboardHistory` imported; `wasi:http/client@0.3.0` and `pane:extension/programs@0.1.0` only if the bundle uses them). Unknown `"pane"` options → error. Base world `js-extension` lives in `guests/js/wit/world.wit`.
7. **WIT assembly**: copies the 16 `PANE_WIT` files from `wit/` into `<staged>/wit/deps/pane-extension/` plus `wit/deps/*.wit` (WASI_WIT).
8. **Componentize**: spawns the componentizer binary: `componentize-qjs-p3 <wit> <world> <bundle.mjs> <runtime.wasm> <out.wasm>` with env `QJS_P3_LIBC=<libc.so>`; last stdout line is JSON `{"component_bytes":N,"componentize_ms":N}`.

## 7. CI: `ci-fast.yml`, `ci-branch.yml` (and `ci.yml`'s js-guests legs)

- **`ci-fast.yml`** (pushes to `pi-subagent/**`): quick tier = `Check (ubuntu/windows)`: `cargo fmt --all --check` + `cargo check --workspace --all-targets` (no wasm, no tests). **`js-guests` job** (ubuntu, runs on every plain push): runs `python3 tools/componentize-js/pane_js.py check`; if stale, installs Node 24 + `rustup toolchain install`, restores the `js-toolchain-<os>-<hashFiles(tools/componentize-js/**, rust-toolchain.toml)>` cache (`~/.cache/pane/componentize-js/{bin,downloads,node}`), runs `pane_js.py samples`, uploads the **`js-guests`** artifact; the agent commits it (`gh run download <run> -n js-guests -D guests/prebuilt`) before a verify run. Verify tier (manual `gh workflow run ci-fast.yml --ref <branch> -f verify=true`): `Lints (ubuntu/windows)` + `Tests (ubuntu/windows, N/3)` + `macos-check`; chosen-tests tier (`-f tests='…'`) on all three OSes. `passed` needs `[check, lints, tests, macos-check, chosen, js-guests]`.
- **`ci-branch.yml`** (every non-main, non-`pi-subagent` branch push; fork PRs): `changes` job (dorny/paths-filter vs merge-base with main; "code" = everything except `docs/**` and top-level `*.md`), `Lints (ubuntu/windows/macos)` = `cargo xtask ci-lints`, `Tests (ubuntu, 1/3–3/3)` = `cargo xtask ci-tests --partition hash:N/3` (shard 1: Xvfb clipboard; shard 2: `cargo xtask file-index-guard`). Doc-only pushes run nothing but the summary. `passed` needs `[changes, lints, tests]`.
- **`cargo xtask ci-lints`** (xtask/src/main.rs): `cargo fmt --check` (root + `guests` + `guests/fixtures/mixed-p2` + `guests/helpers/echo` + `guests/hello-rust`), `pane_js.py check` (prebuilt samples — **this is what gates JS/TS guest staleness**, not the tests), `sdks()`, clippy `-D warnings` (root + echo helper). **`cargo xtask ci-tests`**: `guests()` then `cargo nextest run --locked --workspace --retries 2` (+ options like `--partition hash:1/3`). So JS/TS *tests* are not gated on the script's toolchain — they run the committed `guests/prebuilt` components; only `develop_builds.rs`'s JS/TS legs need the toolchain via `PANE_TEST_JS_BUILDS=1`.
- **`ci.yml`** (main + manual): `js-guests` job gated by paths filter (`guests/**`, `tools/**`, `wit/**`, `Cargo.lock`, `rust-toolchain.toml`, the workflow, `.github/actions/**`): `pane_js.py check`, restore js-toolchain cache, `cargo xtask js-guests`, upload `js-guests` artifact; then `js-guests-tests` (3 Linux shards) downloads the artifact into `guests/prebuilt` and runs `cargo xtask ci-tests --partition hash:N/3` with `PANE_TEST_JS_BUILDS: "1"` — "behaviour is compared, not bytes" (rebuilds aren't byte-identical). One Rust cache per OS saved only by `ci.yml` `Lints (os)` on main (also runs `cargo xtask ci-tests --no-run` there). Composite action `.github/actions/setup/action.yml` (Linux deps + mold scoped to host triple, pinned toolchain only, `Swatinem/rust-cache` with `workspaces: ., guests, guests/fixtures/mixed-p2, guests/helpers/echo`, cargo-nextest 0.9.146 pinned, test opt-ins `PANE_TEST_PROCESS_TREES`/`PANE_TEST_REAL_CLIPBOARD`/`PANE_TEST_SYSTEM_ICONS`, Windows faster TMP drive).
- **Where a new CI job for npm packages / templates fits**: follow the `js-guests` pattern — a paths-filtered job in `ci.yml` (plus its `needs` in `passed`), or reuse `componentizer.yml`'s artifact pattern for per-platform CLI builds; `ci-branch.yml`'s lints/tests already cover any new crate in the root workspace automatically (a job added to a workflow must be added to that workflow's `CI passed` `needs`). New Cargo workspaces that should be cached must be added to `setup/action.yml`'s `workspaces` list. Note `.config/nextest.toml` (fail-fast false, priorities, real-clipboard test group).

## Constraints an implementer must respect

- **Naming** (CONTEXT.md glossary + ADR 0047): the CLI is `pane-ext` (never "Pane CLI"/`pane`); npm scope **`@pane-app`**: `@pane-app/extension` (types/SDK, no CLI inside), `@pane-app/cli` (the tool), `@pane-app/create` (so `npm create @pane-app`); crates.io `pane-extension`; `pane`/`@pane`/`create-pane` were taken (2026-10-08). Glossary: "pane-ext: the command-line tool authors use beside the app to create, develop, check and pack an extension package; it builds with the same code as development mode and hands the result to the running Pane"; "Local channel", "Development mode", "Build failure", "Obsolete build", "Source-only package", "npm-distributed package" (Pane downloads it itself, runs no install scripts, installs no npm deps).
- **ADR 0047 invariants**: one build crate shared by app development mode and `pane-ext` ("the two can never build a package differently" — `pane-build`); `pane-ext` has `new`/`dev`/`check`/`pack` (`publish` later); JS/TS authors need **only Node and npm** (prebuilt componentizer via per-platform `optionalDependencies` chosen by a JS shim; `runtime.wasm` and WASI 0.3 `libc.so` embedded — they're wasm, run everywhere; esbuild an ordinary dependency); Rust authors need only rustup stable + `wasm32-wasip2` and crates.io `pane-extension`; templates: list, detail, form, no-view; `npm run dev` runs `pane-ext` (ADR: "Templates run it through `npm run dev`"); publishing SDKs is a person's step, never CI's. ADR 0045: official extensions live in `pane-app/<id>` repos; the default extensions' source will leave `guests/` and **needs the published SDK and WIT (#128) to build outside a Pane checkout**; `pane-app/extension-template` uses the official-repo layout, builds a release revision on each `v<semver>` tag, and carries an AGENTS.md.
- **ADR 0013 / WASI 0.3**: every component Pane accepts must import only WASI 0.3 (`runtime.rs` `WASI_VERSION "@0.3."`); stock componentize-qjs/jco/StarlingMonkey (P2) are rejected — this is why the patched toolchain and the six-target componentizer exist.
- **CI tiers** (docs/agents/ci.md): branch pushes (non-`pi-subagent`) = branch tier (lints on 3 OSes + Linux test shards) — this is the merge gate; `pi-subagent/**` = ci-fast quick/verify; `componentizer.yml` and `ci.yml` (release matrix, main-only) are never merge gates; no milestone work waits for the release matrix. Every workflow ends in one `CI passed` job; a job added to a workflow is added to its `needs`. Landing: squash-merge each ticket onto the milestone branch, commit titled `… (#NN)`, results comment cites the commit; waves of 3–4 tickets. Stale `guests/prebuilt` makes `ci-lints` fail — commit the `js-guests` artifact before a verify run.
- **Issue tracker** (docs/agents/issue-tracker.md): GitHub Issues `pane-app/pane`; five triage labels (`ready-for-agent`, `ready-for-human`, `needs-triage`, `needs-info`, `wontfix`); native sub-issues of spec #128 + `blocked_by` relationships; acceptance checkboxes + readable "Blocked by" per ticket; close blockers as completed and record actual results.
- **Repo conventions**: `cargo xtask` is the task runner (guests, js-guests, sdks, ci-lints, ci-tests, package-*); Rust pinned 1.98.1 + fmt/clippy/rustfmt components + `wasm32-wasip2` target; workspace deps centralized; `deny.toml` + `NPM_LICENSES` license policy for anything bundled into components; deterministic npm-style tarballs (`PACKED_MTIME`) when one integrity must serve everywhere; tests never reach the network (loopback-only registries/servers, `PANE_NPM_REGISTRY` debug-only).

## Open design questions an implementer must decide

1. **How the shared build crate invokes the componentizer (#218/#219)**: spawn the prebuilt `componentize-qjs-p3` binary (per-platform npm `optionalDependencies`, chosen by a JS shim — ADR 0047's stated plan; needs the argv contract `p3_build <wit> <world> <js> <runtime.wasm> <out.wasm>` + `QJS_P3_LIBC` env kept stable) vs. vendoring the patched componentize-qjs crates into the Rust build and calling `componentize_qjs::componentize` in-process (Wasmtime/Wizer 47 dependency, but no per-platform binary shipping). pane_js.py today does the former; nothing in the repo yet decides it for Rust.
2. **Where `runtime.wasm` + `libc.so` come from in the npm CLI**: ADR 0047 says "the CLI embeds them" (they're platform-independent wasm). Embedding ~1.2 MB + libc into a binary or a shared npm package (`@pane-app/cli-wasm`?) vs. per-platform packages; and how the recorded digests (`toolchain.json`) travel for integrity/version checks.
3. **esbuild/TypeScript versions and the npm-installing staging logic**: `pane_js.py` pins esbuild 0.28.2/TypeScript 7.0.2 from `tools/componentize-js/package-lock.json` and stages `file:../js` devDependencies. In an npm-distributed CLI, `@pane-app/extension` comes from the registry, not `file:../js` — the staging/`package-lock` marker logic must be reworked; who owns tsc/esbuild versions then (the CLI's own deps)?
4. **`pane-ext` binary distribution (#219)**: `xtask/package.rs` packages only the `pane` app today; does the npm `@pane-app/cli` wrap a Rust-built `pane-ext` binary per platform (built where — `componentizer.yml`-style workflow? a new packaging workflow?), and is `pane-ext` also shipped inside the app's installers beside `pane` (its `find_pane` already looks for `pane` beside its own exe)?
5. **Retiring `pane_js.py` vs. keeping it as the prebuilt-samples rebuilder**: `guests/prebuilt`, `cargo xtask js-guests`, and all CI staleness gating (`pane_js.py check`) depend on the script; #219 says "retire pane_js.py" but the repo still needs a way to rebuild the committed samples (the new Rust path in `pane-build`? the npm CLI? keep the script only for CI?). Similarly `PANE_TEST_JS_BUILDS` gating and the `js-guests` artifact flow need a new owner.
6. **`pane-ext dev`'s JS default**: `dev.rs` calls `Toolchains::from_env(None)` so JS/TS dev requires `PANE_COMPONENTIZE_JS`; with the componentizer embedded this disappears, but until then the in-app path (`pane-core` passes the checkout path) and the CLI path differ — decide what an installed (non-checkout) pane-ext does for JS packages pre-#219.
7. **Template home and sharing (#221/#223)**: no template code exists; decide the shared location (data in `pane-core`? a new crate? files in `guests/`?) so both the in-app Create Extension command (embedding) and `pane-ext new`/`npm create @pane-app` (copying) use one source, and what the template set is (list, detail, form, no-view — ADR 0047) in both Rust and TypeScript flavors; `pane-app/extension-template` repo content (#223) must follow ADR 0045's official-repo layout (release revision on `v<semver>` tags, AGENTS.md pointing at docs/WIT/examples) — its relationship to the in-repo templates (generated from them? a separate hand-written repo?) is unspecified.
8. **`pane-ext pack` (#225) format**: the npm-sample path (`xtask` `npm_sample()` + `scripts/npm_publish.py` + `tests/support/npm_registry.rs` `pack()`) shows the deterministic tarball discipline; decide whether `pack` produces an npm tarball ( Pane-installable, `files: [pane.json, *.wasm]`), and whether `check` (stubbed) reuses the host's install checks (`Runtime::check`, manifest parsing) or reimplements a subset — pane-ext currently depends on `pane-core`, so the checks are reachable.
9. **Componentizer version drift**: patches 0003 (async import stubs) is retired by a Wasmtime 49 upgrade upstream, and 0001/0002/0004 have upstream candidates — the pin/patch/digest scheme (`pins.json`, `wasm-parts.json`, `toolchain.json`) must keep working when the queue shrinks; also decide how `componentizer.yml`'s six artifacts get consumed by the npm packaging job (nothing consumes `componentizer-<target>` outside that workflow today).

## Key facts established by reading

- schemars 1.2.2 + schemars_derive 1.2.2 are in the root Cargo.lock (gpui-ce
  transitive); all their deps (dyn-clone, indexmap, ref-cast, serde,
  serde_json) resolve. Adding `schemars = "1.2"` to pane-core adds ONE
  lockfile line ("schemars" in pane-core's deps list), no new packages.
  Source read locally at ~/.cargo/registry/.../schemars-1.2.2 to get the
  1.2 API exactly: `SchemaGenerator::default().into_root_schema_for::<T>()`,
  `Schema` (thin wrapper over serde_json::Value, `ensure_object()`),
  `json_schema!` macro, derive `schemars::JsonSchema` which registers the
  `serde` helper attribute (so `#[serde(rename_all=…)]`/`deny_unknown_fields`
  work without serde derives), doc comments → description (leading `#`
  heading becomes title — avoid), `deny_unknown_fields` →
  `additionalProperties: false`, `#[schemars(with = "Type")]` /
  `#[schemars(schema_with = "fn")]` replace a field's schema (Option/null
  handling must be inside the replacement when the field is nullable;
  required-ness still comes from `#[serde(default)]`).
  Determinism: Schema serializes through OrderedKeywordWrapper ($id, $schema,
  title, description, type, format, properties first; $defs last; the rest in
  Map order) — stable; `serde_json::to_string_pretty`.

## Decisions (with reasons)

1. **Schema location: `guests/js/schema/pane.schema.json`**, added to
   guests/js/package.json `files` so `cargo xtask sdks`'s npm pack carries it
   (spec: "inside the npm packages"). Cost: the JS samples go stale once →
   commit the js-guests artifact (the documented flow). Stable URL per
   manifest version (pane-1.json at a Pane domain) is a person's publishing
   step later; the schema carries no $id until then, only a $comment saying
   it is generated. (The task prompt suggested exactly this.)
2. **Generation lives in pane-core** (`src/schema.rs`), new pub fn
   `manifest_schema() -> String`; xtask calls it. Both the app and pane-ext
   could reuse it later. The serde-layer structs in packages.rs get
   `#[derive(schemars::JsonSchema)]` and pub(crate) visibility; hand-written
   schema types (in schema.rs) cover what raw serde_json::Value cannot:
   `icon` (Icon + Tint + Mask), `preferences` (Preference + dropdown
   options), `arguments` (Argument, maxItems 3 = MAX_ARGUMENTS), `mode`
   (derive JsonSchema on the real CommandMode, kebab-case), `platforms`
   (schema-local PlatformId pinned to Platform::ALL by a test), helper
   `targets` (patternProperties of Target ids), `keywords` (maxItems
   MAX_KEYWORDS). Root post-processing adds `title`, `description`,
   `$comment` and the `manifestVersion` property (const MANIFEST_VERSION,
   required) — the one field the serde layer checks before deserializing.
3. **I cannot run cargo**: the committed schema is generated BY CI. A new
   `schema` job in ci-fast.yml (plain pushes, like js-guests) runs
   `cargo xtask schema`; when stale it regenerates with `--write` and uploads
   the `manifest-schema` artifact; the agent downloads and commits it. My
   initial commit carries a hand-written best-effort placeholder so
   include_str! compiles; CI replaces it with the true bytes.
4. **Drift checking, three layers**: `cargo xtask ci-lints` runs the new
   `cargo xtask schema` compare (branch tier, verify tier, release matrix);
   a pane-core unit test compares include_str! of the committed file with
   the generated one (every tier that runs tests); the ci-fast `schema` job
   regenerates on plain pushes. The quick tier (fmt+check only) cannot run
   any of these without paying a full build on every push — noted in ci.md.
5. **pane-ext check shares pane-core's code**: new `pane_core::check::
   check_package(folder) -> CheckReport` runs Manifest::read (Pane's exact
   messages), then Runtime::check_with per component (all of them, not just
   the first — each message still Pane's, via PackageError::Component), then
   the lint rules. Runtime started inside check_package,
   futures::executor::block_on (pane-core already depends on futures).
   pane-ext check.rs = CLI framing, --json, --deny-warnings, eslint.
6. **Lint rules in pane-core** (check.rs) so Pane can adopt them later;
   eslint invocation stays in pane-ext (a CLI process concern).
7. **Warnings never fail the exit code unless `--deny-warnings`** (the
   flag chosen for "warnings only when asked"; documented in --help).
   Interpretation of "they must not fire on Pane's own samples": the
   repo's own packages must PASS check (exit 0) — samples lack 512 icons
   and descriptions and many titles are not Title Case, so those rules
   are warnings, never errors. The acceptance "every sample … manifest
   validates" is about schema validation + check exit 0.
8. **Cross-target helper files are a WARNING, not the spec's error**: the
   repo's own sample-helper packages are assembled by `cargo xtask guests`
   with only THIS system's helper file (xtask echo_helper builds one), so
   an every-target error would fail Pane's own samples. The current
   system's helper file stays a hard ERROR through Pane's own install
   check (Manifest::read → PackageError::Helper) — the spec's rule for the
   system that matters is still an error with Pane's message; the other
   targets warn.
9. **No JSON Schema validator crate** (Cargo.lock cannot be regenerated
   locally): `check` validates the manifest through Pane's own parse, which
   IS the schema's authority (the schema is generated from the same types);
   a second validator could disagree with Pane and break message parity.
   The committed schema is the editor-facing artifact kept honest by CI.
   This is the ticket's sanctioned fallback ("if schema-conformance cannot
   be done cheaply by hand").
10. **Metadata fields**: author/homepage/repository/issues/license as
    Option<String> trimmed-non-empty (like description); keywords as
    Vec<String> (trimmed, empty entries dropped) bounded by
    MAX_KEYWORDS = 20 (over the bound = InvalidManifest error, Pane's
    wording, shared by install and check).
11. **eslint invocation**: `npm exec --offline -- eslint .` run in the
    package folder (npm.cmd on Windows), only when package.json has eslint
    in devDependencies AND an eslint config is present; --offline keeps it
    to the package's locked local install instead of fetching. npm absent →
    skipped with a note (CI runners have no Node outside setup-node jobs).
12. **--json report**: {"version":1, "folder":…, "ok":…, "errors":[{"id",
    "file","message"}], "warnings":[…], "eslint":{"ran":…,"note":…}} —
    errors exit 1; usage errors exit 2. Human output prints Pane's messages
    verbatim as `error:`/`warning:` lines.

## Lint rules implemented (ids)

Errors: `manifest` (Pane's parse/install refusal, file pane.json),
`component` (Runtime::check failure, Pane's message), `runtime` (the
checker itself could not start).
Warnings: `title-case` (package or command title), `icon` (no icon / PNG
under 512×512 / unreadable PNG), `help` (required preference without a
default and no HELP.md in the package), `description` (none, for
publication), `issues` (neither issues nor repository), `helper-file`
(declared target with no file, cross-system).

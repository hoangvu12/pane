## 1. Extension logs (landed #212/#213)

**Model — `crates/pane-core/src/extension_log.rs`** (pub mod; ~560 lines):
- `ExtensionLogs` (clonable `Arc<Mutex<Logs>>`), keyed by package identity **key string** (`PackageIdentity::key()`).
- Types: `LogSource{Extension(LogStream), Pane}`, `LogStream{Stdout,Stderr}`, `LogLevel{Debug,Info,Warn,Error}`, `LogLine{time: SystemTime, source, level, command: Option<String> (manifest command id), generation: u64, text: String}`.
- Limits: `LINE_LIMIT` 4 KiB (cut + note), `PANE_LINE_LIMIT` 16 KiB (Pane's own lines — "a crash's backtrace may be long"), `LINES_PER_SECOND` 1000 (`Rate::allow` drops + notes dropped), window `WINDOW_LINES`/`WINDOW_BYTES` 500/256 KiB (not developed), `DEVELOPED_LINES`/`DEVELOPED_BYTES` 5000/2 MiB (developed), `FILE_LIMIT` 5 MiB rotation to `<name>.1` (`rotated(path)`).
- API: `output(owner, generation, stream, command: CurrentCommand) -> Output` — a `wasmtime_wasi::cli::StdoutStream` impl (`Lines` splits lines, handles `\r`, partial lines on Drop); `pane(owner, generation, level, text)` (Pane's own messages); `develop(owner, file: PathBuf)` (starts development log, deletes old), `stop_developing(owner)`, `file(owner)`, `lines(owner) -> Vec<LogLine>` (oldest first), `follow(owner) -> Receiver<LogLine>` (ends when development ends), `clear(owner)`, `forget(owner)`.
- Level detection `level_of()`: sd-daemon prefixes `<3>` error, `<4>` warn, `<6>` info, `<7>` debug (written by both SDKs); untagged = info (stdout) / error (stderr).
- `LogLine::file_line()`: `<UTC RFC3339 ms> <level padded 5> stdout|stderr|pane [command] text` — the log file and copy formats.

**Runtime wiring**: `crates/pane-core/src/runtime.rs` (imports at line ~177); `runtime/supervisor.rs` `Shared.logs: ExtensionLogs` (line ~216) — every guest instance's WASI ctx stdout/stderr go to `ExtensionLogs::output`; `CurrentCommand` is set per call so lines are tagged with the running command id.

## 3. Stack traces

- **Rust guest panic**: `guests/pane-extension/src/lib.rs` `#[panic_handler] fn panic` (line ~602) — logs the panic message + location (PanicInfo) as an **error line to the extension log first** (`log.rs` `panicked()` writes `<3>panicked ...` with `file:line:col`), then traps. The trap is caught by wasmtime; the human-readable part for a crash is therefore already in the extension log; the wasm backtrace (raw addresses, no names; workspace builds `debug = "line-tables-only"`, guests release with `panic = "abort"`) rides inside the `CallError::Trap` string → pause.why → PauseDetails/status line. Samples that crash on purpose: `guests/sample-settings` (item "Crash"), `sample-query` ("crash" fallback text), `sample-schedule`/`sample-service`.
- **JS uncaught error**: `guests/js/adapt.js` converts thrown errors into guest-answered errors (never a crash) and `logThrown` (`guests/js/console.js`) writes them **with their stack** (`inspect(Error)` → `"{error}\n{stack}"`) to the extension log at error level. A JS *crash* (resolving with a wrong type) has no stack. `console.trace` writes message + stack at debug.
- **Source maps: none.** The JS/TS build is `tools/componentize-js/pane_js.py build <package> <out.wasm>`: stage package beside `guests/js` types → `node tsc -p tsconfig.json` (type errors reported as `src/index.ts(12,7): error TS2322: …`, run from the staged copy) → esbuild bundle via `tools/componentize-js/bundle.mjs` (**no `sourcemap` option set** — no source map produced) → componentize-qjs (`componentize-qjs-p3` binary, `QJS_P3_LIBC`). So JS stacks name functions in the bundled module, not original source lines.
- **Staged component in development mode**: `pane-build/src/session.rs` — staging folder inside the session's **work folder** (`Pane data dir/develop/<slot>/` for Pane's own sessions; user cache dir for `pane-ext`'s, see `pane-ext/src/dev.rs` `work_folder`); `stage_package` (pane-build/src/build.rs) copies `pane.json` + helper files; the build writes components there; on success `copy_components` also copies them into the **source folder** (e.g. `dist/hello_ts.wasm`, `target/wasm32-wasip2/release/hello_rust.wasm`) so a later Reload reloads the same build. Development samples = `guests/hello-rust` and `guests/hello-ts` (also `hello-js`).

- **`ManifestCommand`** (524): `id, title, subtitle: Option, icon: Option<Icon>, component: PathBuf, platforms, root_results, indexed_results, mode: CommandMode, takes_query, search, schedule: Option<ManifestSchedule>, service: bool, preferences: Vec<Preference>, arguments: Vec<ManifestArgument>` (from `crates/pane-core/src/arguments.rs`; max 3). `CommandMode{View, NoView, Provider}` (489). `ManifestSchedule{every_seconds, item: Option<String>}` (474; bounds MIN/MAX_SCHEDULE_SECONDS 1 s–30 d, `MAX_SCHEDULE_ITEM` 256).
- **`ManifestOperation`** (454): `id, version: u32, component: PathBuf, platforms`. **`ManifestHelper`** (377): `id, targets: BTreeMap<Target, PathBuf>` (pane-target). **`ManifestDependency`** (396): `id, source: String, required: bool, operations: Vec<RequiredOperation{id,version}>, platforms`.
- **JSON layer**: `ManifestJson` (585) is `#[serde(rename_all="camelCase")]` **without `deny_unknown_fields`** → unknown *top-level* fields are silently ignored (forward compatibility; where a new metadata block goes — `description` already there; add `author/homepage/repository/issues/license/keywords` as optional fields). Sub-objects are strict: `HelperJson`, `DependencyJson`, `RequiredOperationJson`, `OperationJson`, `ScheduleJson` carry `#[serde(deny_unknown_fields)]`; `CommandJson` is camelCase, permissive, with `icon/preferences/arguments` as raw `serde_json::Value` validated in code (`icons::parse_manifest_icon`, `preferences::parse`, `arguments::parse`).
- **Validation + exact install-check strings** — `Manifest::parse` (856–1046) and `check_components` (780): "manifestVersion must be 1", "missing field `manifestVersion`", `PackageError::NewerManifest(found)`, `IncompatibleApi`, "`title` is empty", "every command needs an `id` and a `title`", "command id `{x}` contains `#`, which command ids cannot", "command id `{x}` is repeated", mode error text ("a command's `mode` is \"view\" … \"no-view\" … \"provider\""), provider checks (`check_provider`), schedule/argument errors, "every operation needs an `id`", "operation `{x}` has version 0; versions start at 1", helper errors ("unknown target `{x}` of helper `{y}`; use windows, macos or linux, a dash, and x86_64 or aarch64, such as \"linux-x86_64\""), `MissingComponent{command, component}` ("{command} names {component}, which is not in the package"), helper file checks via `runner::check_file`. **This is the shared check path for `pane-ext check`** — pane-ext already depends on pane-core (its `PaneManifest` implements pane-build's `ManifestFiles` using these rules, `crates/pane-core/src/develop.rs`); `Manifest::read(folder)` is `pub` (checks platform + components + icons), `read_parsed` is `pub(crate)` (parse only) — an implementer may need to widen visibility or add a `check` entry point.
- **Schema generation**: there is **no schemars dependency anywhere** (workspace + pane-core Cargo.toml verified). Options: add schemars to `ManifestJson` (needs Serialize + handling of Value-typed icon/preferences/arguments and deny-unknown subtypes), or hand-write the schema and test it against `Manifest::parse` (fixtures exist in `crates/pane-core/tests/packages.rs`). `cargo xtask sdks` (ci.md) already checks SDK packaging and is the natural place to keep a generated schema honest; `cargo xtask ci-lints` runs it in CI.

## 8. Development-mode lifecycle

- **Putting a folder into development**: install the local package (preview → Install, or `Launcher::install_package(folder)`), then the "Develop <title>" row (`Entry::Develop`, from `development_rows`, developing.rs:587 — only enabled local packages) or `Launcher::start_developing(&identity)`. Checks in `begin_developing`: changeable, not already developed, not `Changing` (busy), builder configured (`with_development`), `identity.local_folder()`. Work dir = `<data>/extensions/../develop/<slot>` (`installation.dir.join("develop").join(slot(identity))`).
- **Watcher + rebuild on save**: `pane-build/src/session.rs` — `Prepared::new(builder, manifests, folder, work)` → `(Session, Worker)`; `Worker::start(Host)`. notify watcher; `SETTLE` 150 ms; saves filtered by `is_save`/`Build::ignores` (`target/ node_modules/ dist/`, hidden, editor temporaries, build outputs, `Cargo.lock`); builds one at a time; obsolete builds (save during build) run to completion but are never delivered; after `MAX_OBSOLETE = 3` the session waits for the next save; logs `build.log` / `failed-build.log` in the work folder; `Development{folder, command, building, pending, waiting, finished, obsolete, failure: Option<Arc<BuildFailure{summary, output, earlier, log}>>}` report; `Host` trait `is_current/building/failed/claim/deliver/delivered/installed/gave_up/changed` implemented by `Reloader` in developing.rs (claims under the launcher lock; delivers by running `Reload::staged(identity, staging)` on a current-thread tokio runtime via `Launcher::carry_out`).
- **Reload**: `crates/pane-core/src/launcher/reload.rs` — checked as an install; replaces the managed copy, ends the old generation (ADR 0041 snapshot handoff opt-in), copies components back to the source folder; **startup failure pauses with Retry, no rollback** (ADR 0004). Statuses: "Building {title}: {command}…", "Reloaded {title}", "Reloaded {title}, but it failed to start".
- **Ending**: author stops (`Entry::StopDeveloping`/`stop_developing`), disable/uninstall, Pane quits (`cx.on_app_quit` → `stop_all_development` in app.rs and main.rs); a running build is killed with its process tree (`pane-build/src/process_tree.rs`) before the call returns.
- **Local channel (#217) that `pane-ext dev` uses**: `crates/pane-core/src/local_channel.rs` — `Endpoint` (Windows named pipe `\\.\pipe\pane-<user SID>`; Unix socket `channel` in a 0700 user runtime folder; override env `PANE_CHANNEL`), protocol `VERSION = 1`, JSON lines: `Request` (serde tag "request", kebab-case) = `Develop{folder, staging, command}` / `Building` / `Failed` / `Subscribe` / `Stop`; `Event` = log lines (`LogLine`), `developing`/`refused`/`previewing`, `build`, `ended`. Pane listens in `crates/pane/src/main.rs` (`local_channel::serve(developing, &endpoint) -> (Server, Previews)`; each preview folder → `LauncherWindow::present_package`). Pane-side remote development: `Launcher::develop_remotely(identity, command, BuildNow) -> Result<(Remote, Receiver<LogLine>), String>` (developing.rs:760) — `Driver::Remote` sessions; `Remote` implements pane-build's `Host` (delivers staged builds), dropping it ends development. `pane-ext/src/dev.rs` runs the same `Prepared`/`Session` in the terminal with an `Echo` printing each build line; `pane-ext/src/start.rs` finds/starts the `pane` program (PANE_APP → exe dir → install locations → PATH).

## Constraints an implementer must respect (docs)

- **Issue tracker** (`docs/agents/issue-tracker.md`): work tracked in GitHub Issues `pane-app/pane` via `gh`; tickets use `ready-for-agent`; add implementation issues as native sub-issues with parent URL; check blockers; record actual results before closing; local ticket copies are not maintained.
- **CI** (`docs/agents/ci.md`): ticket work goes on `pi-subagent/**` branches — plain push runs the quick tier (`cargo fmt --all --check`, `cargo check --workspace --all-targets` on Linux+Windows); one manual `gh workflow run ci-fast.yml --ref <branch> -f verify=true` runs lints (`cargo xtask ci-lints`: fmt, prebuilt-samples check, `cargo xtask sdks`, clippy `-D warnings`) and the full nextest suite (3 shards, 2 retries; opt-ins `PANE_TEST_PROCESS_TREES`, `PANE_TEST_REAL_CLIPBOARD` (win/mac), `PANE_TEST_SYSTEM_ICONS` (win)). **JS/TS sample components committed under `guests/prebuilt` must match sources** — CI rebuilds and uploads the `js-guests` artifact which must be committed (`gh run download <run> -n js-guests -D guests/prebuilt`) before verify. Merges: squash each ticket onto the milestone branch as one commit titled "(#NN)", waves of 3–4, never dispatch the release matrix during a milestone; branch tier is the merge gate. Local cargo commands are each developer's own choice — never required. Update ci.md when a leg changes.
- **Domain** (`docs/agents/domain.md`, `CONTEXT.md`): use the glossary vocabulary exactly (Extension log ≠ Pane's log; Build failure ≠ Startup failure; Crash notice; Development mode; pane-ext vs pane; Logs screen = "Logs for <title>"; no "console"/"watch mode"/"hot reload" wording); read `docs/HANDOFF.md` + `docs/current-decisions.md` + relevant ADRs; surface ADR conflicts rather than silently overriding.
- **ADR 0047** (the spec's charter): app-first — Create Extension command (name, Rust or TypeScript, template: list, detail, form or no-view) **writes the folder and starts development mode on it**; Import Extension command for existing source; Logs screen (landed); **error overlay with the stack trace** (ticket #214); thin `pane-ext` with `new/dev/check/pack` (only `dev` exists); one build crate (landed); rejected: jco/StarlingMonkey/stock componentize-qjs (WASI 0.2), Javy, CLI inside the types package.
- **ADR 0045**: official/default extensions live in per-extension repos under `pane-app`, pinned per Pane release; identity `default:<id>` unchanged; the defaults' source leaving `guests/` depends on the published SDK + WIT.
- **ADR 0004** (reload, amended by 0041): saved data survives reload; live state only via opt-in snapshot; **build failure keeps working code**; **startup failure pauses with Retry and does not restore older code**; development save→build→reload keeps the launcher open.
- Related: ADR 0041 (generations, snapshot handoff, undo list), ADR 0043 (extensions managed in Settings only), ADR 0046 (breaking API change = new extension API version).

## Open design questions an implementer must decide

1. **#214 — overlay mechanics**: core-screen vs window-overlay. `Screen::Confirm` is the only "drawn over the current screen" precedent in pane-core; the Actions panel and confirmation focus are window state (`drawn_over`). Decide whether the error overlay is a new pane-core `Screen` variant (works in tests via `LauncherView`) or window state (needs a `drawn_over`-style flag and key context), and how Escape/dismiss interacts with the open command view.
2. **#214 — trigger and content**: which crashes show the overlay (a *developed* package's trap while its command's view is open? any guest trap while developed? the third crash/pause?), and what it shows: the `CallError::Trap` text (which contains the wasm backtrace — raw addresses), the extension-log error line, and/or a link to "Logs for <title>". Note single crashes are currently **not** written to the extension log (only the pause message is, via `Launcher::pause`); `ExtensionLogs::pane`'s 16 KiB `PANE_LINE_LIMIT` and the Logs screen's first-line-truncation were explicitly built for backtraces, so writing each trap (or each *developed* package's trap) into the log looks intended but is not done yet — decide where that hook goes (`note_health`? runtime.rs `crashed`?).
3. **#214 — normal vs development mode**: today the only differences are the development status lines/kept status and the extra rows; the overlay ticket likely scopes to developed packages (ADR 0047 says "an error overlay with the stack trace" in the app-first authoring list) — confirm against the ticket body.
4. **#222 — template source and folder writing**: templates as embedded assets vs a folder beside the binary vs the (future) `pane-app/extension-template` repo; where Create writes (user-picked folder via `choose_folder`, Pane data dir, or a default documents folder) — note Pane otherwise never writes the user's source folder except copying built components back after a successful build; ADR 0047 wants Create to "write the folder and starts development mode on it" (install preview in between? `pane-ext dev`'s first-run preview suggests install-then-develop, `develop_remotely`'s `previewing` flow).
5. **#222 — Import vs existing flows**: "Import Extension" overlaps "Install extension from folder…" + "Develop <title>"; decide whether Import = folder picker → preview → install → auto-start development (and where its row/Settings entry sits; root rows are gated on `installation.is_some()`).
6. **#222 — form**: whether to add a `FormPurpose` variant (core) or drive fields window-side; how the name field sanitizes into a folder name/package title; which Entry variant dispatches it.
7. **#224 — schema generation**: hand-written schema (pinned by tests against `Manifest::parse`) vs adding `schemars` (ManifestJson is Deserialize-only, has raw-Value icon/preferences/arguments and strict sub-objects — a faithful schema needs custom handling); where the schema ships (SDK package `@pane-app/extension`, `pane-ext check --schema`, a docs file) and whether `cargo xtask sdks`/`ci-lints` checks it.
8. **#224 — `pane-ext check` semantics**: does it check a *built* package (`Manifest::read` — requires components present, platform checks) or a *source* folder (parse-only; components absent → explain as source-only, per the glossary)? `Manifest::read` is `pub`, `read_parsed`/`check_components` are `pub(crate)` — a shared check entry point in pane-core may be needed so Pane and pane-ext print identical strings.
9. **#224 — description in Manage extensions**: the group page currently shows only `source_line` under each title; `description_of` exists — decide list-item lines/truncation, and whether the install preview gets the description as a detail line (it has none today).
10. **Metadata block**: exact optional fields (author, homepage, repository, issues, license, keywords) — unknown top-level fields are ignored today, so adding them is backward/forward compatible; decide where each is displayed (extension page? preview?) and their length/format validation, mirroring the existing trimmed-non-empty rule for `description`.

Checks run a few at a time (about four), bounded by existing HTTP limits; staging/apply on the existing path; a package in use is applied when quiet and listed "Waiting until <title> is not in use". ## 7. TICKET #267 SPECIFICS — where each piece goes

- **"Check now" for extension updates**: `Updates::check_now()` (updates.rs:309–314) exists but is `pub(super)`; a public `Launcher::check_extension_updates()` (modeled on `Launcher::check_application_update_again`, application_update.rs:284–289, which distinguishes `asked: bool` — "the user asked, so up to date is an answer, not a silence") would set `next_check = 0`, poke, and mark the pass user-asked so eligibility widens (see #1) and the outcome is always reported.
- **Entry points**: root search — new Pane-own row + `Entry` variant in `root_results` (launcher.rs:3461+, beside the app-update/crash rows; window dispatch in `activation` launcher.rs:2715 + app.rs:1135). Settings — a button row in `group_page` (settings/extensions.rs:≈1100–1130, beside the `extension-updates` switch), plus "Last checked …" text; both run the same new public API, as ADR 0043 requires (two entry points, one flow — see `check_application_update_again`'s doc).
- **Per-source eligibility enums (where each reason is decided)**: pinned npm — `npm.pinned` (record `"pinned": true`; `eligible` updates.rs:717); pinned Git — `git.revision.pinned()` (git.rs:588–590, Tag/Commit); local folder — `identity.local_folder()` / no npm+git (updates.rs:719); development copy — `state.developing`/`is_developed` (extensions.rs:58, `developing.rs`); disabled — `package.enabled`; paused — `state.paused.is_paused` (pausing.rs); automatic-off — `state.update_controls.automatic`/`off` (updates.json); "needs a newer Pane" — `apiVersion` check surfaces as `PackageError` from `read_and_check_from` ("Incompatible package: it needs Pane extension API X, but this Pane provides Y", see test `an_incompatible_new_version_is_refused_with_its_explanation`); "not available on this system" — platform/`platform::unavailable`.
- **HTTP limits**: every Pane-own request goes through `crate::http` with `OWN_LIMITS` (http.rs:762–774): connect 30s, first_byte 60s, between_bytes 60s, deadline 300s; npm metadata ≤ `MAX_METADATA` 16 MiB (npm.rs:41), tarball ≤ `MAX_TARBALL` 64 MiB (npm.rs:43); defaults index ≤ `MAX_INDEX` 1 MiB. "About four at a time" = a small concurrency constant in updates.rs's check loop (today strictly serial — `for package in candidates`).
- **"A package in use" waiting**: `quiet()` (updates.rs:750–772) + `Applied::Deferred` + `RETRY_EVERY` (apply_one 624–660); no user-visible waiting text exists today — the ticket's "Waiting until <title> is not in use" is new copy for the results record/progress.
- **Update keeps disabled disabled / unpauses paused**: disabled packages keep `enabled: false` through `install_plan`+`put_installed` (an update of a disabled package must be allowed by the asked-pass eligibility but the package stays disabled — `Store::update` keeps `enabled`); unpausing a paused package: `put_installed` already calls `self.unpause(state, &identity)` (launcher.rs:3148) — matching the preview's Update row semantics.
- **Retry one package / Update Now**: reuse `check_for_update`-style per-identity paths or add per-identity variants of the pass; the existing per-package Update row on the preview (`Entry::Install(request, Mode::Update(identity), assumptions)`, install.rs preview_view ≈815+) is the "update one now" path.

### Summary of the most important findings

1. **The updater is one self-contained module** — `crates/pane-core/src/launcher/updates.rs` — with a clear pass pipeline (`pass` → `check` (363–413) → `check_npm/check_git` → `stage` (508–583) → `apply/apply_one` (584–712)); results recording naturally hangs off `check`/`apply_one`, and every status-line message it emits today is inventoried above (they are what the tickets replace).
2. **The clock seam is `Launcher::with_clock` + `ManualClock`** (clipboard.rs:515–588): tests advance the clock 2s and `Launcher::wait_for_updates` (launcher.rs:1741) waits for settle — #256's "one minute" is a one-constant change (`FIRST_CHECK_AFTER`, updates.rs:79) plus test updates.
3. **"Check now" already exists** (`Updates::check_now`, updates.rs:309) and has the perfect prior art for a user-asked variant in `Launcher::check_application_update_again` (application_update.rs:284) — including the `asked` flag that makes an all-up-to-date pass an answer rather than silence.
4. **A Pane-own screen + window feature view has a repeatable recipe**: new `Screen` variant (launcher.rs:202), `show_*` in a launcher module (e.g. `developing.rs:400 show_extension_log`), a getter, branches in `refresh` (3363), `actions.rs` (395–509), app.rs render/sync (1750–2030, 1249–1281), and a `features/*.rs` view with its own key context (extension_log.rs is the model). `Screen::Extensions` + `Entry` is the list prior art; only Root/CommandSearch have search fields today.
5. **The toast surface exists (feedback.rs) but cannot carry a Pane-own action like View Details** (`ToastDoes` is only Copy or an extension callback, feedback.rs:143–149) — hence both tickets' "status line carries the same text until the toast surface can carry it"; `show_own_toast` (launcher/feedback.rs:605) + `ToastStyle::Animated` + id/revision updates is the progress-toast mechanism.
6. **"Next time the launcher is shown"** is `Launcher::set_window_presence` (launcher/feedback.rs:203) driven by `Pane::unhide`/`hide` (app.rs:862/885) — the Hidden→Shown transition is where the one-time failure announcement fires; the crash notice (crash_notice.rs) is the one-time-announcement prior art.
7. **updates.json is the persistence pattern to copy** for the results record: versioned serde struct, `open`/`text`, atomic `write_atomically` off-thread, read in `Launcher::create` (launcher.rs:1432).
8. **Settings' Extensions group is `features/settings/extensions.rs`** — the global "Update extensions automatically" switch lives in `group_page` (≈1100–1130); #267's button and "Last checked" go beside it, and everything must run through `Launcher::extension_operations`/`run_extension_operation` (extensions.rs:320/345) per ADR 0043, with the results screen added to `in_extension_flow`/`details_screen` (428–453) so Settings draws it.
9. **Tests**: `pane-core/tests/update.rs` (`Dirs`, `check()` = clock.advance + wait_for_updates, loopback npm `Registry`/git `Server`/`Artifacts`, `hold_update_applies`) is the launcher-interface fixture; `pane/tests/update.rs` + `support/settle.rs` (`until`/`enter_flow`) and `pane/tests/settings.rs` (`open_extensions`, `click_row`, real keystrokes, a11y) are the window fixtures.
10. **Conventions**: no local cargo/rustfmt/xtask ever (CI-only; push the work as `pi-subagent/**` so the fast tier runs); rustfmt defaults (max_width 100, fn_call_width 60, chain_width 60); claim tickets with `gh issue edit … --add-assignee @me`; commits by hoangvu12 <hggaming91@gmail.com> signed-off; squash-merge per ticket with `(#NN)`; #267 stays blocked until #256 lands; #269 is out of scope.

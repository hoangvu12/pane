# Extensions reach the network through wasi:http, sent by Pane

Proposed 2026-09-28 by the implementation of #30; not yet confirmed by the user. An online search command must reach a web service. Before #30 a guest had no network access at all: the WASI context granted no sockets and no `wasi:http` was linked.

Pane links `wasi:http@0.3.0` (the `client` and `types` interfaces, from wasmtime-wasi-http 49.0.1's experimental p3 implementation) for every command, JS/TS and Rust alike. The requests are sent by Pane's own code in the host (`crates/pane-core/src/http.rs`: hyper over HTTP/1.1, TLS with rustls and the ring provider, trusting the system's certificates through rustls-native-certs), not the crate's default sender, whose bundled root list (webpki-roots) carries a license outside deny.toml. The guest SDKs wrap the client in a small `get` (`pane_guest::http`, `@pane/extension/http`); the standard bindings stay available. A request belongs to the guest call that made it: dropping the call (a stopped search, an ended generation) drops the request and closes its connection, and code of an ended generation cannot start one.

This follows [ADR 0013](0013-require-wasi-03.md): a WASI 0.3 interface exists for the job, so no Pane-specific networking API was added, unlike [ADR 0015](0015-host-finds-and-opens-applications-for-an-extension.md), where WASI had nothing. A native helper ([ADR 0014](0014-optional-native-extension-helpers.md)) was not needed either. Raw sockets (`wasi:sockets`) stay denied: libraries built on `wasi:http` work, ones opening sockets themselves do not. Under the trusted-code model ([ADR 0002](0002-trusted-extensions-and-open-distribution.md)) access is not gated per extension or per host.

Costs: every JS/TS component now imports `wasi:http` (the componentizer's snapshot stubs its async `send`, a change to Pane's patch 0003); the p3 implementation is marked unstable upstream and may change with Wasmtime; proxies, HTTP/2 and per-extension network controls are not provided.
